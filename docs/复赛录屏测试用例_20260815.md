# 淘到宝引擎 V2.0 复赛录屏测试用例

版本：V2.0 Final
录制环境：http://8.218.59.190/
建议成片：4 分 30 秒
推荐分辨率：1920×1080，浏览器缩放 90%～100%

## 一、录制目标

用一个连续售前故事展示完整业务闭环：

`磋商前识别客户与项目 → 磋商中快速回应和异议演练 → 生成互动 HTML → 磋商后 Deep Research 与飞书专家协作 → 可信资产沉淀`

录屏重点不是逐页介绍菜单，而是证明：

1. AI 深入售前核心链路，而不是只做聊天摘要。
2. 企业经验、企业能力、公开情报严格分开。
3. 所有正式结论都有来源、边界、风险和待确认项。
4. AI 不知道时会暴露缺口，不会伪造企业依据。
5. 研究结果可以回到飞书，让人类专家接力。

## 二、统一演示场景

客户：A 客户，一家全国性零售企业。
项目：100 家门店视觉质检试点。
目标：90 天完成试点，关注识别准确率、隐私合规、系统集成和预算边界。

推荐快速方案问题：

> A 客户计划在 100 家门店开展视觉质检试点，希望 90 天内上线，并提出识别准确率不低于 95%、预算控制在 50 万元以内。请只基于已校验经验和原子能力给出试点方案；没有企业依据的内容必须标记为待确认。

推荐 Deep Research 问题：

> 在不承诺未经验证指标的前提下，研究 A 客户门店视觉质检试点的技术路线、落地风险、证据缺口和 90 天实施计划，并区分历史事实、企业能力、AI 推断和待确认信息。

推荐演练异议：

1. 你们凭什么保证 90 天内完成上线？
2. 如果识别准确率达不到 95%，你们怎么处理？
3. 门店视频涉及顾客隐私，如何证明方案合规？

## 四、主线录屏测试用例

### DEMO-01：登录与今日工作台

建议时长：20 秒。

操作：

1. 打开 `http://8.218.59.190/`。
2. 完成邀请码验证和飞书登录。
3. 进入今日工作台，快速扫过客户工作、方案与协作、企业知识和系统入口。

预期结果：

- 显示当前飞书用户。
- 首页不是功能堆砌，而是进入客户任务的统一工作台。
- 不出现 Mock、测试 API 或开发调试文字。

建议讲述：

> 售前资料通常散落在飞书文档、妙记和历史方案里。淘到宝从一次真实客户磋商出发，把情报、方案、研究和专家协作连接成一条可信链路。

### DEMO-02：资料库与可信资产底座

建议时长：25 秒。

操作：

1. 打开资料库，展示飞书来源或内置比赛资料。
2. 分别打开一条已校验经验和一条已校验原子能力。
3. 展示来源标题、版本、审核状态、权限状态和更新时间。

预期结果：

- 经验与能力分库展示。
- 只有已校验且来源有效的资产可用于检索。
- 来源快照信息完整，不只显示一个资产 ID。

建议讲述：

> 我们没有把所有材料混成一个向量库。过去做过什么和现在能提供什么分开治理，只有来源、版本、权限都有效的资产才能参与方案生成。

### DEMO-03：磋商前——公开情报与客户画像 Proposal

建议时长：35 秒。

操作：

1. 打开“情报与招标”的情报工作区。
2. 展示一条真实搜索或已完成的历史搜索任务。
3. 打开情报来源，展示 URL、抓取时间、正文摘要和来源快照。
4. 打开客户画像 Proposal，对比修改前后字段。
5. 展示“人工确认后才写入画像”的按钮，但录屏可不重复提交。

预期结果：

- 公开情报标记为 `external_public_information`。
- 搜索摘要不能直接成为企业经验或能力。
- 新情报先形成 Proposal，不会自动覆盖长期客户画像。
- 来源冲突、过期或不可用状态清晰可见。

建议讲述：

> AI 可以发现公开信息，但不能替员工擅自改客户画像。系统先保留网页快照和引用，再提出画像修改建议，最后由员工确认。

### DEMO-04：磋商前——招标解析与响应矩阵

建议时长：35 秒。

操作：

1. 切换到招标工作区。
2. 上传 `淘到宝_招标上传验收测试.docx`；录屏时间紧张时直接打开预解析结果。
3. 展示结构化要求清单。
4. 打开响应矩阵，重点展示一条“有依据”和一条“依据不足”。
5. 展示审核状态及 CSV 导出入口。

预期结果：

- DOCX 上传和异步解析成功。
- 要求项保留原文位置和版本。
- 企业经验和能力证据分别匹配。
- 缺少依据的条目被 Trust Gate 拦截，不生成虚假承诺。

建议讲述：

> 招标文件被拆成逐项响应矩阵。系统可以写草稿，但企业证据不足时只能提示缺口，不能替公司作出承诺。

### DEMO-05：磋商中——快速方案

建议时长：40 秒。

操作：

1. 进入 A 客户的快速方案会话。
2. 输入统一演示问题，或打开预跑结果。
3. 展示方案正文、检索来源、风险和待确认问题。
4. 展示同一客户下的历史会话或追问能力。

预期结果：

- 快速方案读取同一客户画像。
- 经验和能力检索快照分别保留。
- 页面明确显示：
  - `historical_fact`
  - `enterprise_capability`
  - `ai_inference`
  - `pending_confirmation`
- 找不到企业依据时明确拒绝编造。

建议讲述：

> 快速方案不使用 Multi-Agent，重点是速度和可信。历史事实、企业能力、AI 推断和待确认项在页面上分开，销售知道哪些能说、哪些还要确认。

### DEMO-06：磋商中——客户异议与方案演练

建议时长：35 秒。

操作：

1. 从快速方案一键进入方案演练。
2. 展示系统冻结的客户画像和方案上下文。
3. 连续回答 2～3 个客户异议。
4. 打开演练报告，展示得分、扣分原因、知识缺口和改进建议。

预期结果：

- 演练读取固定上下文，不被后续资料变化篡改。
- 系统针对绝对承诺、缺少证据和未暴露风险进行扣分。
- 演练报告不会自动修改画像、方案或可信资产。

建议讲述：

> 这不是替代销售，而是把真实客户异议提前暴露。系统指出回答中缺少的证据和风险，让员工带着问题进入正式磋商。

### DEMO-07：互动 HTML 方案交付

建议时长：35 秒。

操作：

1. 进入演示交付，选择已发布的快速方案。
2. 展示任务状态 `ready`。
3. 点击“打开互动 HTML”。
4. 在新标签页点击顶部章节导航。
5. 点击一次“展开 / 收起”。

预期结果：

- HTML 在桌面浏览器正常打开。
- 页面包含真实方案事实、来源、风险和可信边界。
- 导航滚动、展开和收起正常。
- 产物通过 FactBinding 与安全审计。
- 不需要 PPTX，不依赖服务器运行浏览器。

建议讲述：

> AI 可以负责视觉表达，但没有权力改写事实。正式方案先通过 Trust Gate，再生成互动网页；动画和交互在评委自己的浏览器执行，服务器压力很小。

### DEMO-08：磋商后——Deep Research

建议时长：35 秒。

操作：

1. 进入 Deep Research，打开预跑任务。
2. 展示需求分析、经验检索、能力检索、方案编排和事实审计阶段。
3. 打开研究报告，展示证据冲突、知识缺口和待确认问题。

预期结果：

- Multi-Agent 只出现在 Deep Research。
- 长任务有阶段进度和失败恢复信息。
- 研究结论保留证据快照和可信边界。

建议讲述：

> 复杂问题才进入 Deep Research。多个节点分别做需求分析、经验检索、能力检索、编排和事实审计，而不是让一个模型一次性自由发挥。

### DEMO-09：飞书专家协作

建议时长：30 秒。

操作：

1. 从 Deep Research 打开专家协作。
2. 展示系统推荐的真实作者、贡献者或审核人。
3. 展示待确认问题和群名称。
4. 使用预先创建的飞书群，展示机器人首条研究摘要和研究文档链接。
5. 不在正式录屏中反复点击建群。

预期结果：

- 专家协作绑定同一个 `research_task_id`。
- 没有专家或问题时建群按钮不可用。
- 群名包含客户和研究主题。
- 群成员为淘到宝机器人和已确认人员。
- 首条消息包含客户、研究问题、阶段结论、依据、知识缺口、风险和文档链接。
- 专家回复属于 `pending_confirmation`，不会自动成为已校验经验。

建议讲述：

> AI 负责找到该问谁、把上下文准备好，人类专家负责补齐未知。专家回复回到原研究任务，但仍需人工选择和审核后才能沉淀为企业经验。

### DEMO-10：收束到企业知识闭环

建议时长：20 秒。

操作：

1. 返回资料库或今日工作台。
2. 展示来源、经验、能力、方案、研究和专家协作之间的关系。
3. 以项目价值总结收尾。

预期结果：

- 整条链路能回到来源和审核状态。
- 没有把公开情报、AI 推断或专家回复直接伪装成企业事实。

建议结语：

> 公开情报帮助销售看清机会，可信资产支撑现场回答，Deep Research 和专家补齐未知，最终把每次磋商沉淀为下一次可复用的企业能力。

## 六、录制通过判定

必须全部满足：

- 登录、客户画像、情报、招标、快速方案、演练、Deep Research、飞书专家协作和互动 HTML 均有真实画面。
- 至少展示一条来源快照和一条“依据不足/待确认”结果。
- 至少展示一次人工确认门禁。
- 至少展示一次飞书联动结果。
- 至少展示一次互动 HTML 操作。
- 不展示 Mock 功能成功，不展示密钥和私人数据。
- 不声称 PPTX、移动端适配或 Open Enrich 供应商是本次正式交付能力。

## 七、失败时的录屏备用方案

| 现场问题 | 正确处理 |
|---|---|
| AI 临时超时 | 切换到同一真实环境中的历史成功任务，明确说明为预跑结果 |
| 自动情报临时不可用 | 展示已保存的真实来源或手工来源，不展示虚构搜索结果 |
| DOCX 解析等待过久 | 打开同一文件的预解析 Tender 和响应矩阵 |
| Deep Research 尚未完成 | 展示已完成任务的阶段轨迹、恢复记录和报告 |
| 飞书回调不稳定 | 展示已成功创建的真实群和研究文档，不重复建群 |
| 互动 HTML 生成等待 | 展示已审计且状态为 `ready` 的历史产物 |

备用不是伪造：只能展示系统真实保存的历史任务和产物，不能用静态页面冒充刚刚执行成功。

## 八、录制后检查

- 视频时长控制在 3～5 分钟。
- 所有中文可读，无乱码、问号或页面遮挡。
- 浏览器地址、飞书群和研究文档来自正式测试环境。
- 密钥、Token、用户隐私和后台日志均未入镜。
- 体验地址、邀请码使用说明和 Demo 视频链接可单独复制到参赛方案。
- 最终视频至少保留 3 张关键截图：响应矩阵、四类可信边界、互动 HTML/飞书专家群。
