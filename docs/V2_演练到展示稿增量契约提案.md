# V2 演练到展示稿增量契约提案

## 1. 为什么需要拍板

当前 `CreatePresentationRequest` 只有 `style_profile_id`、`mode`、`audience`、`output` 和 `language`，不能表达使用哪次演练、员工选了哪些建议及其可信边界。

因此当前代码只生成安全候选交接包，没有先修改冻结接口，也没有把演练评价自动塞进展示稿。

## 2. 建议的最小增量

建议新增员工确认交接接口：

```text
POST /api/v1/rehearsals/{rehearsal_id}/presentation-handoff
```

请求：

```json
{
  "selected_sections": [
    "high_frequency_objections",
    "recommended_answers",
    "risks",
    "knowledge_gaps",
    "pending_questions"
  ]
}
```

响应应使用 `rehearsal-presentation-handoff-v1`，包含员工选择的 `narrative_context`，同时强制 `fact_ledger_writes: []` 和 `auto_applied: false`。

## 3. 后端保存建议

优先保存为单独不可变记录，至少包含 `rehearsal_id`、报告 ID 和版本、操作员工和时间、所选栏目、交接包快照、可选 `presentation_id` 和状态。

不要写入 `ClaimRecord`、`EvidenceRecord` 或 FactLedger。

## 4. 展示稿使用规则

1. 展示稿创建仍先通过现有 Trust Gate；
2. released claims 和有效 evidence 仍是唯一事实来源；
3. handoff 只进入 `narrative_context`，用于客户异议、风险提示和备答；
4. handoff 中的数字、案例或能力不得直接展示为事实；
5. Presentation Service 为 `mock` 时继续显示真实降级状态；
6. 员工未主动选择时，展示稿完全不读取演练报告。

## 5. 需要组长决定

1. 使用独立 handoff 接口，还是给展示稿请求增加可选 `rehearsal_handoff_id`；
2. 是否新增 handoff 数据表；
3. 推荐回答放正文还是演讲者备忘；
4. 展示稿生成后是否允许再次选择并局部重生成。

拍板前保持现状最安全：演练报告有候选包，但不自动进入展示稿。
