# 淘到宝引擎：企业级能力边界与升级路线

文档状态：本地产品基线候选版  
适用分支：`feat/local-deployment`  
评估日期：2026-08-28

## 1. 结论先行

当前版本已经从比赛 Demo 改造成了一个可配置、可持久化、不会用 Mock 冒充真实功能的
Local First 产品候选版。它适合以下场景：

- 单台 Windows 电脑上的个人试用、产品验证和内部演示；
- 在可信局域网内，由少量已知用户进行试点；
- 使用真实 PostgreSQL、Redis、AI Provider 和可选飞书服务完成业务验收；
- 验证资料、画像、可信资产、快速方案、Deep Research、情报、招标和演练的业务闭环。

当前版本**不能直接被定义为企业级生产服务**。主要原因不是业务页面数量不足，而是企业生产所需的
身份治理、高可用、密钥托管、可观测性、灾备、容量治理、文件安全、合规和运维体系尚未完整交付。

更准确的产品分级是：

| 等级 | 当前结论 | 允许用途 |
|---|---|---|
| 开发/演示 | 可用 | 本机开发、功能演示、自动化测试 |
| 单机试用 | 基本具备 | 真实模型、真实资料、小规模个人使用 |
| 部门级试点 | 有条件可用 | 可信内网、少量用户、有人值守、先完成 P0 安全加固 |
| 企业生产 | 尚不具备 | 必须完成本文 P0、P1 建设及正式验收 |
| 关键业务/大规模服务 | 尚不具备 | 还需高可用、异地灾备、容量压测、合规认证和长期运营能力 |

## 2. 评估口径

本文把能力分为四种状态：

- **已实现**：代码中存在真实业务路径，并有自动化测试或历史真实环境证据；
- **有条件可用**：代码已存在，但必须配置真实数据库、模型、飞书或搜索服务后才能工作；
- **局部实现**：主数据结构或后端流程存在，但入口、治理、运维或真实环境验收不完整；
- **未实现/不可承诺**：当前没有完整生产实现，或没有足够证据支持对外承诺。

测试替身只用于自动化测试，不计为生产能力。历史比赛环境的成功记录也不等同于当前本地部署已经完成
同样的实机验收。

## 3. 当前已经能做什么

### 3.1 本地部署与基础运行

| 能力 | 状态 | 当前边界 |
|---|---|---|
| Docker Compose 一键编排 | 已实现 | 编排 PostgreSQL/pgvector、Redis、API、Worker 和前端入口 |
| Windows 启停、状态、日志脚本 | 已实现 | 面向 PowerShell；启动脚本可生成首次运行凭据 |
| 自动数据库迁移 | 已实现 | API 启动前执行 `alembic upgrade head`，失败时不继续提供业务服务 |
| 数据持久化 | 已实现 | PostgreSQL、Redis AOF 和文件目录使用 Docker Volume |
| 配置化端口和监听地址 | 已实现 | 默认仅 `127.0.0.1`；用户可主动启用局域网监听 |
| 健康检查 | 已实现 | 可检查 API、数据库、Redis、AI 和可选集成状态 |
| 备份 | 局部实现 | 已有数据库和文件备份脚本；恢复仍是文档化人工流程，尚未形成定期恢复演练证据 |
| 多机、高可用部署 | 未实现 | 当前 Compose 是单机形态，存在单点故障 |

### 3.2 模型与外部服务

| 能力 | 状态 | 当前边界 |
|---|---|---|
| OpenAI Schema 兼容 Chat Provider | 有条件可用 | 通过服务端环境变量或工作区配置接入；必须使用真实 Key |
| Chat 与 Embedding 分开配置 | 已实现 | 支持独立模型、Base URL 和 Key；Embedding 维度变化需要重建向量 |
| API Key 服务端保存和脱敏返回 | 已实现 | 工作区 Key 加密落库；接口和页面只返回掩码 |
| 通用 Provider 管理 | 局部实现 | 协议可配置，但管理页面的供应商目录和运维能力仍偏向现有 Provider |
| 飞书 OAuth、文档、妙记及协作 | 有条件可用 | 需要企业应用、权限、回调地址和真实联调；关闭时明确不可用 |
| 公开情报 | 有条件可用 | 阿里云搜索或可选 Open Enrich 需要真实凭据；不会回退假搜索结果 |
| 邮件集成 | 未实现 | 当前不能承诺邮件通知、专家邮件协作或邮件归档 |
| AI 用量监控 | 局部实现 | 已有受监控凭证保护的调用汇总及部分 Token 统计；未配置凭证返回 503，尚无完整预算、配额和计费治理 |

### 3.3 核心业务能力

| 模块 | 状态 | 当前能做的事情 | 当前限制 |
|---|---|---|---|
| 资料库 | 有条件可用 | 飞书链接、妙记和粘贴文本进入真实 Source/Job/审核流程 | 通用本地资料上传入口未完全统一；飞书能力依赖真实授权 |
| 客户画像 | 已实现 | 长期画像、版本、状态和 Proposal 人工确认 | 组织级字段权限、批量治理和数据保留策略未完成 |
| 历史经验 | 已实现 | 独立提取、审核、来源有效性判断和检索 | 需要真实 Chat/Embedding；大规模索引尚未压测 |
| 企业原子能力 | 已实现 | 与历史经验分开管理、审核和检索 | 需要真实 Chat/Embedding；尚无企业主数据对接 |
| 快速方案 | 有条件可用 | 读取画像、可信经验和可信能力，生成结构化方案与证据边界 | 模型不可用时明确失败；没有大并发与成本 SLA |
| Deep Research | 有条件可用 | 创建长任务、阶段状态、检索、冲突、事实审计和研究报告 | 真实模型长任务、故障恢复和高并发仍需本地生产环境验收 |
| 专家协作 | 有条件可用 | 依赖研究上下文，候选人来自真实贡献关系，回复回流原任务 | 真实专家回复到研究恢复的完整企业场景仍需专项验收；无邮件渠道 |
| 情报与画像 Proposal | 有条件可用 | 保存真实来源、快照、审核及画像变更提案 | 自动搜索依赖外部 Provider；没有持续采集调度和企业级爬取配额治理 |
| 招标响应 | 已实现/有条件可用 | PDF、DOCX、XLSX、TXT 或正文进入解析、要求拆解、证据匹配和缺口拦截 | 扫描件 OCR 不能作为已验证能力承诺；复杂文档兼容性需样本库验收 |
| 方案演练 | 有条件可用 | 模拟角色与异议，评估证据和危险承诺 | 依赖真实模型；评估分数尚未完成企业场景校准 |
| 互动 HTML | 有条件可用 | 从完成的研究上下文生成并执行事实、安全门禁 | 需要真实生成 Provider；浏览器兼容和视觉验收不等于事实审计 |
| 历史 PPTX 风格 | 局部实现 | 后端存在安全解析、风格画像、模板和审核数据结构 | 当前前端上传入口明确未接通，不能宣称完整可用 |

### 3.4 可信规则

以下规则是当前产品必须继续保留的业务底座，企业化过程中不得为了性能或易用性绕过：

1. 历史经验和企业原子能力分开存储、审核和检索。
2. 只有已审核且来源仍有效的资产可以进入在线召回。
3. 原文更新、删除或权限失效后，旧资产保留追溯但暂停检索。
4. 输出区分 `historical_fact`、`enterprise_capability`、`ai_inference` 和
   `pending_confirmation`。
5. 找不到企业依据时拒绝编造，并显示知识缺口。
6. 每次运行保留独立检索快照和证据关系。
7. AI 的 `recommended_action` 只是建议，最终结果由后端 Trust Gate 决定。
8. 专家回复回到原研究任务，但不能自动成为已审核经验。
9. 公开情报不能绕过原文快照、URL 安全校验、引文绑定和人工画像审批。

## 4. 当前明确不能做什么

### 4.1 不能把单机 Compose 当作高可用服务

当前数据库、Redis、API、Worker 和文件卷都位于同一台电脑。电脑断电、磁盘损坏、Docker Desktop
异常或人为删除 Volume 都可能导致整体中断。`restart: unless-stopped` 只能重启进程，不能解决宿主机、
磁盘、网络或机房故障。

### 4.2 不能把本地管理员账号当作企业身份系统

本地认证用于单机启动，管理员用户名和密码来自环境变量。当前没有完整的：

- 员工入离职自动同步；
- SSO、MFA、条件访问和设备策略；
- 管理员、审核员、销售、专家、只读审计员等角色权限；
- 工作区成员邀请、冻结、强制下线和会话中心；
- 字段级、记录级和敏感正文访问控制。

现有 `workspace_id` 查询隔离是必要底座，但它不等于完整多租户和 RBAC 产品。

### 4.3 不能直接暴露到公网

当前本地 Caddy 提供 HTTP 入口，默认配置没有企业域名证书、WAF、DDoS 防护、统一限流、Bot 防护、
来源 IP 策略和完整安全响应头基线。即使把 `HOST` 改成 `0.0.0.0`，也只代表允许局域网访问，
不代表可以安全暴露到互联网。

### 4.4 不能承诺企业级数据安全与合规

当前已做到密钥不进入前端、Git 和普通接口响应，并进行了日志字段脱敏；但尚未形成：

- KMS/Vault/HSM 托管和密钥自动轮换；
- 数据库、对象存储和备份的企业密钥加密策略；
- 数据分级、保留期限、合法删除和离职交接流程；
- DLP、敏感信息识别、下载水印和导出审批；
- 可供审计的管理员操作日志、登录日志和数据导出日志；
- 等保、ISO 27001、SOC 2 或客户安全评估证据。

因此目前不能对外宣称“满足某项合规认证”。

### 4.5 不能承诺容量、性能和服务等级

当前没有基于目标企业数据量完成正式容量模型和压力测试，不能承诺：

- 同时在线人数、每秒请求数和长任务并发数；
- 百万级资料或向量规模下的检索延迟；
- 99.9%/99.95% 可用性；
- 明确的 RPO、RTO 和故障恢复时间；
- 固定的 AI 响应时延和费用上限。

### 4.6 不能把所有页面入口视为完整交付

后端数据结构、测试和页面入口同时存在，并不自动代表生产闭环已经验收。例如历史 PPTX 上传入口仍明确
提示未接通，扫描 PDF 的 OCR 也没有足够证据作为正式承诺。正式销售材料必须以本文的能力表和最新
验收报告为准。

## 5. 企业级目标架构需要具备什么

企业部署至少应从“单机应用”升级为以下职责分离的体系：

| 层次 | 企业级目标 |
|---|---|
| 接入层 | 企业域名、TLS、负载均衡、WAF、限流、请求大小限制和统一安全响应头 |
| 身份层 | OIDC/SAML/飞书 SSO、MFA、SCIM/通讯录同步、RBAC、会话和离职回收 |
| 应用层 | 多实例无状态 API、版本化配置、滚动发布、熔断、超时和幂等 |
| 任务层 | 可水平扩展 Worker、任务租约、重试/死信、阶段恢复、优先级和租户配额 |
| 数据层 | 托管或高可用 PostgreSQL/pgvector、连接池、只读副本、PITR 和迁移门禁 |
| 缓存层 | 高可用 Redis、认证、TLS、内网访问、容量和淘汰策略 |
| 文件层 | S3/OSS/MinIO 对象存储、服务端加密、版本、生命周期、病毒扫描和签名 URL |
| 密钥层 | KMS/Vault 托管、最小权限、轮换、吊销、访问审计和应急密钥流程 |
| AI 网关 | Provider 白名单、模型路由、超时重试、预算、限额、内容安全和数据出境策略 |
| 可观测层 | 指标、日志、链路、业务审计、告警、看板和事件响应 |
| 交付层 | CI/CD、镜像签名、SBOM、依赖扫描、数据库迁移审批、灰度与回滚 |
| 治理层 | 数据分类、保留/删除、审计导出、供应商评估、隐私和合规证据 |

## 6. 必须完成的升级路线

### 6.1 P0：生产安全底座

P0 未完成前，不允许公网生产和大范围真实客户数据接入。

#### A. 企业身份与权限

要做：

1. 引入企业 SSO，优先采用标准 OIDC；飞书登录作为一个 Identity Provider，而不是业务代码中的唯一身份。
2. 新增工作区成员关系和角色模型，至少包含系统管理员、工作区管理员、销售、审核员、专家和只读审计员。
3. 为所有写接口建立后端权限矩阵，不能只依赖前端隐藏按钮。
4. 增加 MFA/条件访问对接、用户禁用、强制下线、会话撤销和安全登录审计。
5. 增加跨工作区、越权对象 ID、已离职用户和权限撤销的负向测试。

验收标准：未授权请求稳定返回 401/403；跨工作区访问没有侧信道；用户停用后已有会话立即失效；
管理员能够导出用户和权限变更记录。

#### B. 网络与入口安全

要做：

1. 使用企业域名和受信任 TLS 证书，强制 HTTPS 和安全 Cookie。
2. 数据库、Redis、Worker 和对象存储只放在私网，不发布宿主机端口。
3. 在网关实施限流、请求体限制、上传超时、IP/地域策略和 WAF 规则。
4. 为 OAuth 回调、HTML 产物、下载地址和管理接口分别定义 CSP、CORS 和缓存策略。
5. 完成外部渗透测试和修复闭环。

验收标准：互联网扫描无法访问内部服务；TLS 和 Cookie 策略通过安全基线；匿名用户无法访问任何管理配置。

#### C. 密钥与配置治理

要做：

1. 将 AI Key、飞书 Secret、数据库密码和会话密钥迁移到 KMS/Vault/云密钥服务。
2. 应用通过工作负载身份读取密钥，生产环境不再依赖人工分发 `.env`。
3. 建立密钥创建、审批、轮换、吊销和泄露应急流程。
4. 日志、Trace、异常平台和支持工单统一执行敏感字段清洗。
5. 工作区自带 Key 应使用信封加密，并记录谁在何时更新和测试了连接。

验收标准：Git、镜像、浏览器、API、日志和监控中均无法恢复密钥；轮换密钥无需重新构建镜像。

#### D. 数据、文件和备份安全

要做：

1. PostgreSQL 使用企业托管实例或经过验证的高可用方案，启用传输加密和静态加密。
2. 文件从本地 Volume 迁移到对象存储，增加租户前缀隔离、版本、签名 URL 和生命周期策略。
3. 所有上传文件执行 MIME/扩展名复核、压缩炸弹防护、恶意软件扫描和内容解析沙箱。
4. 建立每日备份、PITR、异地副本、备份加密和保留策略。
5. 每季度执行恢复演练，记录实际 RPO/RTO；恢复不是只看“备份任务成功”。

验收标准：能够在隔离环境从备份恢复完整数据库和文件，并验证资料、画像、任务、方案、快照和审核记录一致。

#### E. AI 与可信链安全

要做：

1. 建立企业 AI Gateway，集中控制 Provider、模型版本、数据保留、地域、预算、限额和失败策略。
2. 对资料、搜索结果和专家回复执行提示注入隔离，外部文本不得成为系统指令。
3. Trust Gate 和四类事实标签必须保留为后端强制规则。
4. 每次模型、Prompt、Embedding 或重排策略升级都运行可信回归集。
5. 对缺失证据、冲突证据、过期来源、权限撤销和恶意文档建立红队用例。

验收标准：模型输出不能绕过 Trust Gate；模型不可用或结果不合规时任务明确失败、降级或进入人工复核。

### 6.2 P1：可靠性、运维与规模化

P1 完成后，才具备部门级到企业级生产运行基础。

#### A. 高可用和扩缩容

- API 至少双实例，通过负载均衡健康检查滚动发布；
- Worker 支持多实例竞争任务，验证租约、幂等、重复执行和故障接管；
- PostgreSQL 配置自动故障转移和连接池；
- Redis 使用高可用服务并启用认证/TLS；
- 本地文件状态全部迁出应用实例，使 API 和 Worker 真正无状态；
- 对长任务设置租户级并发、优先级、超时和死信处理。

#### B. 可观测性

至少建设：

- API 延迟、错误率、流量和饱和度指标；
- Worker 队列长度、任务阶段耗时、重试、失败和租约过期指标；
- PostgreSQL 连接、慢查询、锁、磁盘和向量检索指标；
- Redis 内存、命中率、连接和持久化状态；
- AI Provider 成功率、首 Token 延迟、总耗时、Token 和费用；
- 飞书、公开情报、文件解析和 HTML 生成的依赖状态；
- 业务指标：资料待审核量、过期来源、被 Trust Gate 拦截的方案、知识缺口和人工复核积压。

每条告警必须关联负责人、严重级别、处理手册和升级路径。

#### C. 发布工程

要建立：

1. Pull Request 评审、分支保护和冻结契约自动检查。
2. 单元、集成、数据库、浏览器、真实 Provider 冒烟和安全测试分层流水线。
3. 镜像漏洞扫描、依赖许可证扫描、SBOM 和镜像签名。
4. 数据库迁移的向前兼容、备份、审批、灰度和回滚方案。
5. 开发、测试、预生产、生产环境隔离，禁止共用数据库和密钥。
6. 发布后自动冒烟、指标观察和一键回滚。

#### D. 容量与性能

先确定业务规模，再压测，不能先写一个“支持万人”的数字：

- 员工数、工作区数、客户数；
- 资料总量、平均大小、每日增量；
- 经验和能力向量数量；
- 快速方案峰值并发；
- Deep Research 同时运行数和平均时长；
- 招标文件大小、页数和解析并发；
- 每月模型 Token 和搜索调用预算。

用这些数据测试 API、Worker、数据库、pgvector、对象存储和模型网关，形成容量上限、扩容阈值和成本模型。

### 6.3 P2：企业治理与产品完善

P2 用于从“能稳定运行”升级为“企业可以长期采购和治理”。

- 完整管理后台：组织、用户、角色、空间、Provider、配额、数据保留和审计导出；
- 数据分级：公开、内部、机密、客户敏感等标签及处理策略；
- 生命周期：归档、法定保留、用户删除、客户项目结束和离职交接；
- DLP、导出审批、水印和异常批量下载告警；
- 企业知识连接器：对象存储、SharePoint、Confluence、企业网盘等按真实需求建设；
- 通知中心：飞书、邮件或企业 IM，带重试、退订和审计；
- 通用资料文件入口和批量导入；
- 扫描件 OCR、复杂表格和大型招标文件的受控解析沙箱；
- 模型评测平台：业务黄金集、事实性、召回率、拒答率、危险承诺率、成本和延迟回归；
- 多语言、无障碍、浏览器兼容和企业 UI 可用性验收；
- 支持体系：SLA、值班、故障公告、客户支持、升级窗口和版本生命周期。

## 7. 推荐实施顺序

| 阶段 | 建议周期 | 目标 | 退出条件 |
|---|---:|---|---|

| 1. 安全试点 | 3–6 周 | 完成 SSO/RBAC、HTTPS、密钥、对象存储、备份恢复和基础监控 | 安全评审通过，可接入受控真实数据 |

## 9. 本地产品基线转正前的最小验收

即使暂时不做企业高可用，当前 Local First 候选版也必须完成以下实机验收后，才能标记为正式本地产品基线：

1. 在一台从未运行过本项目的 Windows 电脑上完成一键启动。
2. 验证数据库从空库自动升级到唯一 Alembic Head。
3. 修改前后端端口后仍能登录、访问 API 和查看健康状态。
4. 验证 `127.0.0.1` 不可被局域网访问，`0.0.0.0` 在明确放行后可访问。
5. 重启全部容器，确认资料、画像、任务、方案、Redis 和上传文件仍存在。
6. 执行备份，并在新的空 Volume 中完成一次真实恢复。
7. 使用真实 Chat 和 Embedding 导入示例资料，经人工审核后完成真实检索。
8. 运行一次快速方案，核对四类事实标签、引用、风险和待确认项。
9. 创建并完成一次 Deep Research，验证阶段进度、失败恢复、冲突和事实审计。
10. 关闭飞书和公开情报，确认本地核心流程仍运行且页面明确显示不可用。
11. 开启飞书后完成 OAuth、文档、妙记、权限失效和专家回复回流验收。
12. 扫描 Git、镜像、浏览器、接口和日志，确认没有 API Key、Secret、Cookie、Token 或敏感正文泄漏。
13. 对根 `openapi.yaml` 和 `app/contracts/ai.py` 做冻结契约差异检查。
14. 运行全量测试、Lint、迁移检查和关键浏览器流程，并保存可追溯报告。

## 10. 企业生产发布门禁

满足下列条件前，发布结论必须保持“试点”而不是“企业生产”：

- P0 项全部完成并经过安全评审；
- 至少完成一次备份恢复、主机/实例故障和 Worker 中断演练；
- 已定义且实测 SLO、RPO、RTO、容量上限和费用上限；
- 生产无 Mock Provider，外部能力缺失时明确失败或禁用；
- 企业身份、权限、审计和离职回收闭环通过；
- 文件安全、密钥托管、数据保留和删除流程通过；
- Trust Gate、来源失效、权限撤销和拒绝编造回归通过；
- 有预生产环境、发布审批、监控告警、回滚和值班手册；
- 真实业务负责人、安全负责人、技术负责人共同签署验收。

## 11. 对外表述建议

当前可以这样描述：

> 淘到宝引擎已具备 Local First 候选版本，可在单机 Docker 环境中配置真实模型、持久化数据并运行
> 可信售前业务流程；飞书和公开情报作为可选真实集成，未配置时明确降级。当前正在进行企业生产所需的

- “已经满足等保、ISO 27001 或 SOC 2”；

- “AI 生成结果可以不经审核直接作为企业承诺”。

## 12. 最终判断

当前代码已经具备继续企业化的业务骨架和可信数据模型，不需要推倒重做。建议保留 FastAPI、现有领域模型、
PostgreSQL/pgvector、数据库持久任务、五方法 AIEngine 冻结契约和 Trust Gate，在外围逐步替换单机基础设施并
补齐企业治理。

最优路线不是继续增加演示页面，而是依次完成：

1. Local First 实机转正验收；
2. 身份、权限、密钥、HTTPS、文件和备份恢复；
3. 高可用、可观测、CI/CD、容量和灾备；
4. 数据治理、合规、企业连接器和长期运营体系。

完成 P0 和本地实机验收后，可以进入受控部门试点；完成 P1、生产发布门禁和企业安全验收后，才适合定义为
企业级生产服务。
