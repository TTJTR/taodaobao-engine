# 淘到宝引擎合作伙伴代码更新操作手册（GitHub 网页版）

## 1. 协作方式

后续合作伙伴统一通过 GitHub 网页版参与项目，不要求安装 GitHub Desktop。所有正式代码以 GitHub 私有仓库为准，不通过压缩包、微信文件或飞书附件互相覆盖整份项目。

标准流程：

```text
接受仓库邀请
  → 在 GitHub 网页查看任务和最新集成分支
  → 创建自己的功能分支
  → 使用 Codespaces 或本地开发工具修改
  → Commit 并 Push
  → 在 GitHub 网页创建 Pull Request
  → 另一名成员审核
  → 合并到集成分支
  → V1 整体验收后合并到 main
```

## 2. 应该使用哪些工具

| 用途 | 使用工具 | 说明 |
|---|---|---|
| 仓库、分支和提交记录 | GitHub 网页版 | 项目代码的唯一正式来源 |
| 小型文档修改 | GitHub 网页编辑器或 `github.dev` | 适合 Markdown、配置说明等小改动 |
| 正式代码开发和测试 | GitHub Codespaces | 从浏览器打开完整 VS Code 和终端，不需要 GitHub Desktop |
| 本地开发（可选） | Codex、VS Code 或 PyCharm | 开发者熟悉本地环境时可以使用 |
| 代码审核与合并 | GitHub Pull Request | 禁止直接把开发代码写入 `main` |
| 需求与决定 | 飞书文档或飞书群 | 记录任务范围、接口决定、验收和阻塞 |

GitHub 网页编辑器不能替代完整测试环境。业务代码、数据库、AI 或飞书集成修改应使用 Codespaces 或本地环境，并执行测试后再提交。

## 3. 分支的用途

| 分支 | 用途 | 更新规则 |
|---|---|---|
| `main` | 已验收、可以正式部署的稳定版本 | 只允许通过 Pull Request 合并 |
| `v1-integration` | V1 日常集成、联调和验收 | 只允许通过 Pull Request 合并 |
| `feat/*` | 新功能 | 每项任务建立一个分支 |
| `fix/*` | 缺陷修复 | 每个问题建立一个分支 |
| `docs/*` | 独立文档更新 | 不混入业务代码 |

当前最新集成候选分支是：

```text
feat/v1-integration-acceptance
```

在 `v1-integration` 建立并包含这批代码之前，合作伙伴应从 `feat/v1-integration-acceptance` 创建功能分支。以后统一从 `v1-integration` 创建，不能从旧的 `main` 或 `feat/gateway` 开始。

## 4. 管理员如何邀请合作伙伴

1. 在浏览器打开：`https://github.com/wxh042/xianjintuan-engine`。
2. 点击仓库顶部的 `Settings`。
3. 左侧选择 `Collaborators`。
4. 点击 `Add people`。
5. 输入合作伙伴的 GitHub 用户名或邮箱。
6. 合作伙伴在 GitHub 通知或邮件中接受邀请。

这是私有仓库，合作伙伴必须接受邀请后才能查看代码、创建分支或提交 PR。

## 5. 每次开始任务前先写清楚什么

在飞书任务或群消息中确认：

- 任务名称和负责人；
- 本次修改的功能；
- 从哪个集成分支开始；
- 预计修改的模块和文件；
- 上游和下游依赖；
- 是否影响 `openapi.yaml`、AI 五方法、数据库或环境变量；
- 本次明确不做的内容；
- 验收方法。

一个任务对应一个功能分支。不要把飞书 OAuth、AI Prompt、页面改版和云部署等多个无关任务放入同一个分支。

## 6. 如何在 GitHub 网页创建功能分支

1. 打开仓库首页。
2. 点击左上方当前分支名称。
3. 先搜索并切换到当前集成基线：`feat/v1-integration-acceptance`。
4. 再次打开分支选择器。
5. 输入新分支名称，例如 `feat/feishu-oauth-scope`。
6. 点击 `Create branch: feat/feishu-oauth-scope from feat/v1-integration-acceptance`。
7. 确认页面左上方已经显示新分支。

分支命名示例：

```text
feat/feishu-oauth-scope
feat/feishu-tenant-token
feat/feishu-event-callback
feat/cloud-deployment
fix/ai-profile-normalization
docs/deployment-guide
```

禁止直接在 `main` 页面点击编辑并提交。

## 7. 如何直接在网页修改小文件

适用于 README、Markdown 文档和非常小的配置修改。

1. 确认页面当前处于自己的功能分支。
2. 打开目标文件。
3. 点击右上角铅笔图标 `Edit this file`。
4. 修改内容并查看 `Preview` 或 `Changes`。
5. 点击 `Commit changes`。
6. 提交说明使用明确格式，例如：

```text
docs(deployment): clarify cloud environment variables
```

7. 在弹窗中确认提交到当前功能分支，不能提交到 `main`。

也可以在仓库页面按键盘 `.`，打开浏览器版 VS Code（`github.dev`）。`github.dev` 适合多文件文本修改，但没有完整服务器环境，不能运行项目测试。

## 8. 如何用 GitHub Codespaces 开发代码

正式业务代码推荐使用 Codespaces：

1. 在仓库页面切换到自己的功能分支。
2. 点击绿色 `Code` 按钮。
3. 切换到 `Codespaces` 页签。
4. 点击 `Create codespace on <自己的分支>`。
5. 等待浏览器中的 VS Code 打开。
6. 在编辑器中修改代码。
7. 打开终端安装依赖：

```bash
uv sync --extra dev
```

8. 根据模块运行测试：

```bash
export PYTHONPATH=.
uv run --extra dev pytest -q
uv run --extra dev ruff check app tests
git diff --check
```

9. 点击左侧 `Source Control` 查看全部修改。
10. 只暂存属于本任务的文件。
11. 填写提交说明，执行 Commit。
12. 点击 `Sync Changes` 或 `Push`。

如果仓库没有开通 Codespaces，合作伙伴可以使用本地 Codex、VS Code 或 PyCharm 开发，再通过 Git 命令 Push；PR 的创建和审核仍统一在 GitHub 网页完成。

## 9. 提交规范

提交说明采用：

```text
<类型>(<模块>): <本次具体修改>
```

示例：

```text
feat(feishu): add tenant token provider
fix(ai): normalize experience evidence status
test(research): cover expert reply resume
docs(deployment): add cloud setup guide
```

不要使用：

```text
update
修改
test
123
```

建议每完成一个独立、可验证的小功能提交一次。不要几天都不提交，也不要为了“方便”把所有文件一起提交。

## 10. 提交前必须验证什么

通用检查：

```bash
git status --short
git diff
git diff --check
uv run --extra dev pytest -q
uv run --extra dev ruff check app tests
```

按模块追加验证：

| 修改内容 | 必须验证 |
|---|---|
| AI Prompt、Schema、算子 | AI 测试、Mock 回归、黄金案例、引用和可信边界 |
| HTTP 接口 | 路由测试、响应 Schema、冻结接口差异 |
| 数据库 | Alembic 迁移、升级、约束和回滚风险 |
| 飞书 | Mock 测试、测试企业登录、权限、文档、机器人和事件回调 |
| 前端 | 页面加载、主要操作、接口错误态和浏览器回归 |
| 部署 | Docker 构建、迁移、健康检查、HTTPS 和环境变量 |

测试失败时不要写“已经完成”。PR 中必须注明失败命令、错误、影响范围和下一步负责人。

## 11. 如何在 GitHub 网页创建 Pull Request

Push 完成后：

1. 返回 GitHub 仓库网页。
2. 页面通常会显示刚 Push 分支的提示，点击 `Compare & pull request`。
3. 如果没有提示，点击仓库顶部 `Pull requests` → `New pull request`。
4. 设置分支：
   - `base`：当前集成分支；现阶段为 `feat/v1-integration-acceptance`，以后为 `v1-integration`。
   - `compare`：合作伙伴自己的 `feat/*` 或 `fix/*` 分支。
5. 检查 `Files changed`，确认没有无关文件、密钥和真实客户资料。
6. 填写标题和 PR 描述。
7. 添加另一名成员作为 `Reviewer`。
8. 点击 `Create pull request`。

PR 描述模板：

```markdown
## 本次更新
- 任务：
- 模块：
- 实现结果：

## 修改范围
- 主要文件：
- 上游依赖：
- 下游影响：

## 契约和配置
- openapi.yaml：未修改 / 已增加 V1 增量契约
- AI 五方法签名：未修改 / 需要共同评审
- 数据库迁移：无 / 有
- 新增环境变量：无 / 有

## 验证
- 自动测试：
- 人工测试：
- 测试结果：

## 未完成和风险
- 未完成：
- 风险：
- 回滚方式：
```

## 12. 如何审核 Pull Request

审核人在 GitHub 网页执行：

1. 打开 `Pull requests`，进入待审核 PR。
2. 阅读 `Conversation` 中的目标、测试和风险。
3. 打开 `Files changed`，逐文件检查。
4. 有问题时点击对应代码行的 `+` 添加评论。
5. 点击 `Review changes`：
   - 需要修改：选择 `Request changes`；
   - 可以合并：选择 `Approve`。
6. 确认自动测试和人工验收通过后再合并。

审核至少确认：

- 功能符合已确认需求；
- 没有破坏冻结契约；
- 没有写死结果伪装接口；
- 没有真实密钥和客户敏感数据；
- 测试结果可信；
- 数据库和部署变化有说明；
- 未完成项和风险写清楚。

## 13. 审核要求修改时怎么办

不要关闭原 PR，也不要重新创建分支。继续在原功能分支修改并 Push，原 PR 会自动更新。

使用 Codespaces 时：

1. 在 PR 页面点击 `Code` 或回到对应分支创建/打开 Codespace。
2. 根据评论修改。
3. 重新运行测试。
4. Commit 并 Push。
5. 在 PR 中回复已处理内容，请审核人再次检查。

## 14. 如何合并

满足以下条件后，负责人在 PR 页面点击 `Squash and merge` 或团队确认的合并方式：

- 至少一名其他成员已批准；
- 自动测试通过；
- 人工验收通过；
- 无未解决评论；
- 无密钥、客户资料或无关文件；
- 数据库和部署变化可执行。

合并后点击 `Delete branch` 删除远程功能分支。下一个任务必须重新从最新集成分支创建新分支，不能继续使用已经合并的旧分支。

## 15. 两个人同时开发如何避免覆盖

1. 开工前在飞书群声明任务、分支和预计修改文件。
2. 每人使用自己的功能分支。
3. 尽量不要同时修改同一个契约或数据库迁移。
4. 共享文件变更必须提前确认。
5. 出现冲突时逐段确认双方逻辑，禁止整文件覆盖。
6. 不确定时保留冲突现场，把 PR 链接和冲突文件发给负责人。

以下文件发生冲突时必须共同评审：

```text
openapi.yaml
docs/openapi-v1-incremental.yaml
后端_开发/ai.py 对应的五个冻结方法
app/db/models.py
alembic/versions/*
pyproject.toml
```

## 16. 绝对不能上传什么

- `.env` 和任何真实 App Secret、API Key、数据库密码；
- 飞书 `user_access_token`、`tenant_access_token` 和 Cookie；
- 真实客户资料、内部文档正文和个人信息；
- 本地数据库、日志、缓存和虚拟环境；
- 无法说明来源的大批量生成文件；
- 为通过验收而写死的接口结果。

密钥已经进入 GitHub、PR 或聊天记录时，不能只删除文本；必须立即撤销旧密钥、生成新密钥并检查 Git 历史。

## 17. 什么时候可以进入 main

只有同时满足以下条件，才能从集成分支向 `main` 创建发布 PR：

1. 产品确认发布范围。
2. 前端、后端、AI 和数据库集成测试通过。
3. 真实飞书登录、资料权限、文档读取、机器人和回调通过。
4. 云端 Docker、迁移、HTTPS 和健康检查通过。
5. 没有高优先级阻断缺陷。
6. 验收报告、部署说明和回滚方式已更新。

`main` 合并后，由部署负责人使用该提交或版本标签发布。任何人都不能只在云服务器上临时改代码而不回写 GitHub。
