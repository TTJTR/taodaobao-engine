# V1.1 展示效果优化后续开发方案

## 1. 文档目的

当前系统已经完成历史 PPT 风格提取、敏感内容隔离、FactLedger、EvidenceGuard、SlideSchema、
确定性 HTML Renderer 和后台生成流水线，但最终演示稿仍属于“结构正确、视觉基础”的工程样稿。

本阶段目标不是推翻可信架构，而是在不放松事实边界的前提下，将演示效果提升到可用于客户演示的水平。

## 2. 当前问题

### 2.1 已完成能力

- 历史 PPT 的 Theme、Master、Layout 和脱敏内页视觉特征提取。
- 事实、证据、来源和权限的冻结账本。
- Claim、Evidence、Source 和逐字符原文校验。
- Title、KeyMessage、EvidenceCard 三类语义组件。
- Jinja2 自动转义、CSS 变量和无 JavaScript 的确定性 HTML 输出。
- Presentation 状态机和 HtmlArtifact 持久化。

### 2.2 效果不佳的根因

1. 页面组件只有三种，无法表达指标、对比、流程、时间线、能力组合和来源清单。
2. `layout_token` 只是字符串，没有受限模板、插槽和内容容量定义。
3. 当前模板将组件纵向排列，没有真正的页面构图。
4. Planner 没有字符预算、页面目的、信息层级和组件数量约束。
5. Renderer 没有文本测量、字号回退、溢出检测和图片裁切。
6. 没有截图回归和可量化的视觉验收门禁。
7. HTML 和未来 PPTX 导出尚未共享同一套布局坐标模型。

## 3. 核心原则

1. AI 只能输出 SlidePlan，不输出 HTML、CSS、坐标代码或 PPTX。
2. FactLedger 仍是唯一事实源；布局前执行 FactBinding 预检，布局后执行最终 EvidenceGuard。
3. StyleProfile 只决定视觉 token，不携带客户事实。
4. LayoutTemplate 只定义插槽和容量，不改写业务内容。
5. Renderer 只消费已校验 SlideSchema，不访问业务数据库或调用 AI。
6. HTML Renderer 和 PPTX Renderer 必须消费同一份已校验布局结果。
7. 视觉失败只能调整布局、分页、字号或组件选择，不能改写数字与事实。

### 4.4 PptxGenJS：后续 PPTX 导出

PPTX 导出阶段优先评估 PptxGenJS。它适合按照已经计算好的坐标、字体、Shape 和图片生成 PPTX，
但不得成为事实组织器，也不得重新解释 SlideSchema。

## 6. Schema 调整

### 6.1 LayoutToken

第一阶段冻结以下模板枚举：

```text
cover
section
title_body
two_column
three_cards
metric_highlight
comparison
timeline
process
evidence_grid
summary
```

每个模板必须声明：

- 固定画布比例。
- Slot 名称、位置和允许的组件类型。
- 每个 Slot 的最大组件数、字符数和行数。
- 标题、正文和来源区域的最小字号。
- 允许的降级模板。

### 6.2 新增语义组件

P0：

- `MetricComponent`：只显示账本中已验证数字，强制 FactBinding。
- `ComparisonComponent`：左右事实必须分别绑定 Claim。
- `TimelineComponent`：每个节点独立绑定 Claim 或明确为 label_only。
- `ProcessComponent`：步骤事实独立绑定，连接关系不能创造能力。
- `SourceListComponent`：只读取 FactLedger 中的 Source 快照。

P1：

- `ImageComponent`：只引用已审核资源 ID，不接受任意 URL。
- `VerifiedChartComponent`：数据点使用 numeric token 引用，Renderer 不接收自由数字。
- `CapabilityMapComponent`：能力节点只能引用 enterprise_capability Claim。

### 6.3 PositionedSpec

Layout Engine 在 FactBinding 预检通过后生成确定性几何结果：

```text
x, y, width, height
z_index
text_style_token
overflow_policy
image_fit
```

坐标统一使用 0-10000 的逻辑画布单位，HTML 和 PPTX Renderer 分别转换为 CSS 与 PPTX 单位。

布局前为每个事实组件计算内容指纹，指纹覆盖组件类型、原始内容、claim_id、evidence_ids 和 source_ids。
Layout Engine 只能把原组件放入插槽，不能重建或改写组件。最终 EvidenceGuard 重新计算指纹，并再次检查
PositionedSpec 中的 FactBinding 与 FactLedger；任何内容、数字或绑定变化都必须 fail closed。

## 7. Layout Engine

新增文件建议：

```text
app/presentation/layouts/registry.py
app/presentation/layouts/models.py
app/presentation/layouts/templates.py
app/presentation/layouts/selector.py
app/presentation/layouts/fitter.py
app/presentation/layouts/diagnostics.py
```

职责：

- `registry.py`：注册模板，拒绝未知 layout token。
- `models.py`：定义 Canvas、Slot、Capacity、PositionedComponent。
- `templates.py`：实现首批 11 种模板。
- `selector.py`：根据 SlidePlan 目的和组件组成选择模板。
- `fitter.py`：分页、字号回退、插槽分配和降级模板选择。
- `diagnostics.py`：返回溢出、空插槽、密度过高和对比度问题。

禁止职责：

- 改写文本。
- 修改数字。
- 创建 Claim 或 Evidence。
- 调用 LLM。

### 7.1 双阶段校验

布局前的 `FactBinding Validation` 负责尽早拒绝未知 Claim、越界 Evidence/Source、非法组件类型和
不一致的 verbatim 内容，避免为非法方案继续计算布局。布局后的 `Final EvidenceGuard` 复用同一套
事实规则，并校验布局前后的内容指纹，保证分页、插槽分配和字号回退没有改变任何事实。

两个阶段由同一个 `EvidenceGuard` 提供不同入口，不能复制两套规则：

```text
validate_bindings(slide_plan, ledger) -> ValidationReport + fingerprints
validate_positioned_spec(positioned_spec, ledger, fingerprints) -> ValidationReport
```

## 8. Molly 与 Harness 对接

Molly 负责：

```text
plan_slides(planning_context, fact_catalog, style_constraints) -> SlidePlan
```

SlidePlan 只包含：

- 页面目的。
- 推荐 layout token。
- 使用哪些 claim_id。
- 组件意图和信息优先级。
- 每页字符预算。
- 可分页标记。

Molly 不负责：

- 输出 HTML/CSS。
- 输出绝对坐标。
- 生成或修改数字。
- 选择 FactLedger 之外的企业能力。
- 绕过 EvidenceGuard。

所有 Molly 调用继续经过组长 Harness，由 Harness 负责超时、重试、trace、Schema 校验和 Mock/Live 切换。

## 9. HTML Renderer 改造

### 9.1 模板结构

```text
app/templates/presentation/
  base.html
  layouts/
    cover.html
    two_column.html
    three_cards.html
    metric_highlight.html
    comparison.html
    timeline.html
    process.html
    evidence_grid.html
  components/
    title.html
    metric.html
    evidence_card.html
    source_list.html
```

### 9.2 必须实现

- CSS Grid 与逻辑坐标两种渲染方式。
- 16:9 固定画布和响应式等比缩放。
- 文本框 `overflow: hidden`，禁止内容撑开画布。
- 服务端字符预算检查。
- 浏览器端实际尺寸检测，仅上报，不修改事实。
- 图片资源白名单、固定裁切策略和占位降级。
- 页面编号、来源脚注和 FactBinding 调试标记的可控显示。

## 10. PPTX Renderer

PPTX 不从最终 HTML 反向转换。正确方式是：

```text
Validated PositionedSpec
  → HTML Renderer
  → PPTX Renderer
```

两种 Renderer 共享：

- 坐标。
- Style token。
- 组件内容。
- FactBinding。
- 图片裁切参数。

PPTX Renderer 初期可以采用 Node/PptxGenJS sidecar，后端通过内部任务接口传递已校验 JSON。输出后使用
LibreOffice headless 转 PDF/PNG 做自动验收。

## 11. 视觉校验

新增 Playwright 验收：

1. 桌面 1440×900。
2. 笔记本 1366×768。
3. 移动预览 390×844，只验证缩放和无重叠，不改变演示稿比例。

每一页检查：

- 页面非空白。
- 元素不越界。
- 文本不溢出。
- 元素之间不异常重叠。
- 标题、正文、来源脚注不互相遮挡。
- 颜色对比度达到可读标准。
- 所有事实组件仍具有 FactBinding。

视觉失败处理顺序：

```text
缩小非关键间距
→ 使用允许范围内的字号回退
→ 切换降级模板
→ 拆分为两页
→ 标记 needs_review
```

禁止通过删数字、缩写事实或让 AI 自由改写来解决溢出。

## 12. 分阶段实施

### 阶段 A：视觉基准与模板内核，P0

- 建立 10-20 份 Golden SlideSchema。
- 实现 LayoutTemplate/Slot/Capacity Schema。
- 实现 cover、title_body、two_column、three_cards、evidence_grid。
- 将现有 Renderer 改为模板注册表分发。
- 增加 Playwright 截图、越界和非空白检查。

验收：五种模板在三个视口无越界、无重叠、无文本撑开画布。

### 阶段 B：业务组件，P0

- 新增 Metric、Comparison、Timeline、Process、SourceList。
- 扩展 FactBinding 与 EvidenceGuard。
- 增加字符预算和确定性分页。

验收：数字篡改仍 100% 拦截，至少覆盖 80% 当前方案页面表达。

实施状态（2026-08-11）：已完成。Metric、Comparison、Timeline、Process、SourceList 均已使用
Discriminated Union 强类型接入；对比项、时间线节点、流程步骤和来源条目分别绑定 FactBinding。
确定性分页发生在 FactBinding 预检之前，时间线每页最多 4 项、流程最多 5 步、来源最多 6 条；
渲染后仍执行逐绑定账本校验和整组件内容指纹校验。

### 阶段 C：Molly SlidePlan，P0

- 冻结 Planner Protocol 和 SlidePlan Schema。
- Mock Planner 切换为 Molly Mock/Live，经 Harness 注入。
- Layout Engine 对 Molly 推荐模板保留最终否决权。

验收：AI 输出中不存在 HTML/CSS/自由数字，非法 claim_id 无法进入 Renderer。

实施状态（2026-08-11）：后端侧已完成。已冻结 SlidePlan v1、SlidePlanner Protocol、Mock/Live
适配器和 PresentationPlanningHarness；AI 只返回 purpose、layout_token、component_type、claim_ids、
priority、character_budget 与 allow_pagination。SlidePlanMaterializer 从 FactLedger 原文构造 SlideSchema，
Live 模式不支持时明确失败且绝不静默回退 Mock。Molly 仍需在 Live AIEngine 中实现冻结的 plan_slides
算子并提供专项评测结果。

### 阶段 D：PPTX 导出，P1

- 实现 PositionedSpec 到 PptxGenJS 的确定性映射。
- 增加字体缺失替代规则。
- 使用 LibreOffice 转图并做页面数量、空白页和溢出检查。

验收：HTML 与 PPTX 页面数量、组件数量和事实文本一致。

### 阶段 E：视觉评分与人工反馈，P1

- 保存 RenderDiagnostics 和截图地址。
- 支持用户选择“太密、太空、层级弱、风格不像”等结构化反馈。
- 反馈只影响 StyleProfile、布局和 Planner，不修改 FactLedger。

## 14. 数据库与 API

阶段 A-C 不建议新增业务表，继续复用：

- `Presentation.spec` 保存 PositionedSpec。
- `HtmlArtifact.render_report` 保存诊断摘要。
- `HtmlArtifact.preview_screenshot_keys` 保存截图。

当需要保存多次视觉尝试时，再新增 `PresentationRenderAttempt`，字段包括：

- presentation_id/version/attempt。
- layout_diagnostics。
- screenshot_keys。
- failure_codes。
- renderer_version。
- created_at。

现有生成、查询和导出 API 可保持不变。后续可在 PresentationResponse 中增量增加：

- `render_report`。
- `preview_urls`。
- `needs_review_reasons`。

## 15. MVP 暂不实现

- 自由拖拽编辑器。
- 任意 HTML/CSS 模板上传。
- AI 直接生成图片、图表数值或页面代码。
- 复杂动画和交互脚本。
- 对历史 PPT 逐像素复制。
- SmartArt 全量兼容。
- 任意第三方图片 URL。
- 多人实时协同编辑。

## 16. 验收指标

### 事实安全

- FactBinding 覆盖率：事实组件 100%。
- 未知 Claim/Evidence/Source 拦截率：100%。
- verbatim 数字和文本篡改拦截率：100%。

### 工程质量

- 全量测试保持通过。
- Renderer 不依赖 AI、数据库和网络。
- 未知模板和组件 fail closed。
- HTML、截图和 PPTX 产物均可追溯到同一 spec/version。

### 视觉质量

- Golden 页面非空白率：100%。
- 元素越界率：0%。
- 不合理重叠率：0%。
- 文字溢出率：0%。
- 首批模板覆盖常见方案页面：至少 80%。
- 人工盲评中“可直接向客户展示”比例：MVP 至少 70%。

## 17. 推荐下一步

下一次编码只做阶段 A，不同时启动 Molly Live 和 PPTX 导出：

1. 冻结 `LayoutTemplate`、`Slot`、`Capacity` 和 PositionedSpec。
2. 从 Presenton 移植模板注册与容量校验思想。
3. 实现首批五个模板。
4. 用当前 FactLedger Mock 数据生成 Golden 页面。
5. 使用 Playwright 截图验证三个视口。

阶段 A 验收通过后，再让 Molly 接入 SlidePlan。这样可以区分“AI 规划问题”和“Renderer 布局问题”，
避免两者同时变化导致无法定位效果缺陷。
