# V1.1 历史 PPT 风格映射与 Renderer 升级方案

## 1. 文档目标

> 版本边界：本文中的 `StyleProfile v2`、`style-profile-v2` 仅表示 V1.1 演示链路内部的第二版风格数据 Schema，
> 不代表组长下发的产品阶段 V2，也不引用 V2 指标、接口或业务 PRD。产品 V2 必须另行评审、建分支和冻结契约。

本阶段不推翻 FactLedger、FactBinding、EvidenceGuard、SlidePlan、LayoutEngine 和双 Renderer 架构。
目标是解决当前测试暴露的问题：历史 PPT 已提取出颜色、字体、形状与坐标，但进入 Renderer 后只剩基础色板、字体和
固定 `layout_token`，导致不同参考稿生成的页面只是“换色换字体”，结构和组件皮肤几乎完全一致。

目标链路：

```text
历史 PPTX
  -> SafePPTXParser（只读取视觉白名单）
  -> StyleFeatureSet（脱敏原始视觉统计）
  -> StyleProfileBuilder（聚类、归一化、置信度）
  -> StyleProfile v2（DesignTokens + ComponentSkins + LayoutArchetypes）
  -> CandidateTemplate Preview（候选模板预览与人工确认）
  -> TemplateCompiler（编译为受限 LayoutTemplate）

FactLedger -> Molly SlidePlan -> Materializer -> Schema Validation / FactBinding 预检
  -> ProfileScoped LayoutEngine -> PositionedSpec
  -> RenderIRBuilder -> RenderIR Schema Validation -> EvidenceGuard 终检
  -> HTMLRenderer / PPTXRenderer
  -> Artifact Content Audit -> Playwright / PowerPoint 视觉门禁
```

## 2. 当前问题与根因

三个真实样本的技术验收均通过，但人工查看 PowerPoint PNG 后视觉质量不通过：

- 卡片面积过大，内容集中在中部，留白失衡。
- 标题字号直接按历史基础字号比例放大，部分达到不合理尺寸。
- 正文统一垂直居中，没有卡片标题、正文、来源脚注的层级。
- 边框统一使用辅助色，未学习历史 PPT 的圆角、粗细、填充与装饰规律。
- 三份参考稿虽提取出不同布局模式，最终仍落到同一套固定 `two_column` 坐标。
- `layout_grammar` 是字符串，Renderer 无法可靠消费其中的坐标、频率和置信度。

根因不是“已有 Renderer 不能使用”，而是提取结果与 Renderer 中间缺少结构化编译层。

## 3. 不可破坏的边界

1. StyleProfile 只携带视觉和叙事规则，不携带历史 PPT 的业务文本、数字或客户名称。
2. AI 只能输出 SlidePlan，不输出 HTML、CSS、PPTX、绝对坐标、颜色或字体。
3. TemplateCompiler 与 Renderer 均为确定性代码，不调用 AI、数据库或网络。
4. 历史几何特征只能编译为白名单模板，不能直接成为任意自由坐标代码。
5. TemplateCompiler 不创建、删除、合并或改写事实组件。
6. HTML 与 PPTX 必须消费同一份通过终检且冻结的 RenderIR，不得分别解释 PositionedSpec 或 StyleProfile。
7. 布局前检查 FactBinding；RenderIR 构建完成后重新检查事实指纹；视觉优化不能修改任何事实文本和数字。
8. 每个可见文本节点必须声明受限的内容来源，禁止以“普通标签”名义绕过 FactBinding。
9. 文本换行、字号、字体回退和行框由唯一的 TextLayoutEngine 计算，Renderer 不得再次独立排版。

## 4. 开源代码采用策略

### 4.1 可直接移植或改造

#### aiden0z/pptx-renderer

重点复用：

- `RenderContext` 的页面尺寸、坐标与继承上下文思想。
- `TextRenderer` 的文本框内边距、段落、行距、对齐、字号与字体映射。
- `ShapeRenderer` 的填充、边框、圆角和透明度映射。
- Theme、Master、Layout、Placeholder 的继承解析；当前项目已有一部分 Python 移植。

迁移要求：保留 Apache-2.0 notice；只移植视觉计算，不移植历史业务正文读取和展示逻辑。

#### Presenton

重点复用：

- Template、Layout、Element 的分层模型。
- 受限模板注册和 Schema 到 HTML Fragment 的分发模式。
- 模板容量检查和渲染前验证。

迁移要求：将自由内容字段替换为当前项目的 SemanticComponent 和 FactBinding，不采用模型生成页面代码的部分。

#### Presentation AI

继续复用当前已移植的 OOXML relationship、`clrMap`、Theme Palette、Font Scheme 算法，并补充主题字号层级、
shape fill/line 和 layout usage frequency 的结构化产出。

#### PptxGenJS

继续作为 PPTX 写入引擎，复用其文本、Shape、表格和图片的确定性 API。PptxGenJS 只负责写 OOXML，不能承担
模板选择、事实组织和内容改写。

### 4.2 只参考设计、不直接复制

- SeaSlides 的 Strategist -> Executor -> Renderer 分层和 Build Feedback。
- DeepSlides 的 Content -> Slide Design -> Implementation 分层。
- 任何让 LLM 输出自由 HTML/CSS、任意坐标、数字或业务陈述的实现。
- 任何允许上传可执行模板、JavaScript 或任意外部图片 URL 的实现。

## 6. StyleFeatureSet 设计

StyleFeatureSet 是解析器内部的脱敏统计，不直接对外展示：

```text
StyleFeatureSet
  canvas: width, height, aspect_ratio
  color_samples: color, role, frequency, page_coverage
  font_samples: family, size_pt, weight, role, frequency
  shape_samples: kind, normalized_geometry, fill, line, radius_hint
  page_samples:
    normalized_boxes
    title_band
    column_count
    card_grid
    image_region
    density
  master_layouts: placeholder roles and normalized geometry
```

安全规则：

- 不保存 `<a:t>`、图表值、备注、OLE、嵌入对象或链接目标。
- 坐标统一归一化到 0-10000。
- 颜色和字号按频率统计，不保留其原始文本上下文。
- page sample 只保存 `shape_1/shape_2` 等匿名标识。

## 7. StyleProfile v2 设计

### 7.1 DesignTokens

```text
DesignTokens
  colors:
    canvas, surface, primary, secondary, accent, text_primary, text_muted, border
  typography:
    display, title, subtitle, body, evidence, footnote
    每级包含 font_family, size_pt, weight, line_spacing, color_token
  spacing:
    page_margin, section_gap, component_gap, card_padding
  shape:
    radius, border_width, border_style, shadow, surface_fill
  decoration:
    title_rule, accent_bar, page_number, header_footer
```

字号不能无限继承历史值，必须经过安全范围归一化：

- display：32-48 pt
- title：26-38 pt
- subtitle：20-28 pt
- body：16-24 pt
- evidence：14-20 pt
- footnote：10-14 pt

保留历史 PPT 的层级比例，但超出范围时整体缩放，禁止出现当前测试中的超大标题。

### 7.2 ComponentSkins

```text
ComponentSkin
  token
  applies_to
  fill_token
  border_token / border_width
  radius
  padding
  heading_style
  body_style
  alignment
  vertical_alignment
  accent_placement
```

第一批冻结：`plain_text`、`outline_card`、`filled_card`、`accent_bar_card`、`metric_focus`、
`comparison_split`、`timeline_nodes`、`process_steps`、`source_footer`。

正文默认顶部对齐；只有指标和封面允许垂直居中。卡片标题与正文必须分开创建文本框，不能再拼成一个字符串。

### 7.3 LayoutArchetype

```text
LayoutArchetype
  archetype_token
  purpose
  frequency
  confidence
  slots:
    role, normalized_geometry, allowed_components, capacity
  preferred_skin_tokens
  fallback_archetype
```

MVP 白名单：

- `cover_centered`
- `cover_left_aligned`
- `title_body`
- `title_two_column`
- `title_three_cards`
- `metric_with_evidence`
- `comparison_split`
- `timeline_horizontal`
- `process_horizontal`
- `evidence_grid`
- `source_list_compact`

历史 PPT 的几何聚类只能映射到这些白名单 archetype。无法可靠匹配时回退到系统模板，不允许自由执行历史坐标。

## 8. TemplateCompiler

TemplateCompiler 是本阶段最关键的新层：

```text
StyleProfile v2 + system archetype registry
  -> 选择置信度足够的 LayoutArchetype
  -> 将匿名历史 slot 映射为 title/body/card/image/evidence 角色
  -> 应用画布边距和最小间距
  -> 校验容量、重叠、越界和最小字号
  -> 产生只读 CompiledLayoutTemplate
```

编译失败处理：

1. 尝试同 archetype 的安全坐标修正。
2. 切换到该 archetype 的系统 fallback。
3. 仍失败则标记 `STYLE_TEMPLATE_UNUSABLE`，禁止进入 Renderer。

TemplateCompiler 只编译视觉模板，不读取 FactLedger，也不接触组件文字。

## 9. Renderer 升级

### 9.1 共享渲染语义

HTML 和 PPTX 不再分别解释 ComponentSkin，而是共同消费冻结后的 RenderIR：

```text
PositionedSpec
CompiledStyle
  -> RenderIRBuilder
  -> RenderIR
       canvas: width / height / aspect_ratio / coordinate_unit / scale_mode
       layers
       TextNode / TextRun
       ShapeNode / ImageNode / TableNode / VerifiedChartNode
       geometry / padding / alignment / fill / stroke / shadow / clipping
       content_origin / fact_trace / user_trace / system_label_token / asset_trace
       resolved_font / font_file_hash / font_size / line_height / line_breaks / line_boxes
       renderer_contract_version
```

RenderIR 是 Renderer 唯一允许消费的输入。HTMLRenderer 和 PPTXRenderer 只能将同一节点映射到各自运行时，
不能再次选择模板、解释 StyleProfile、计算业务布局或修改文字。该设计直接借鉴 Presenton Template v2 中
`TextRun/Font/Fill/Stroke/Shadow/Padding/Alignment/Flex/Grid` 的场景模型，但删除自由业务内容入口，
为事实节点增加 `fact_trace`，为资源节点增加 `asset_trace`。

每个 `TextRun` 必须包含 `content_origin`，且只能取以下白名单值：

- `ledger_verbatim`：必须携带完整 `fact_trace`，文本逐字符等于 FactLedger 中冻结的 `verbatim_text`。
- `ledger_label`：必须携带 `fact_trace`，只允许使用 FactLedger 明确允许的显示标签。
- `user_authored`：必须携带用户消息或已确认输入的不可变快照 ID 与哈希。
- `system_label`：只能引用版本化的后端白名单文案 token，不能直接接收 AI 自由文本。

装饰节点不能携带文本。不存在合法来源分类或所需追踪信息不完整的文本节点必须 fail closed，不能进入 Renderer。

每份 RenderIR 必须包含 SHA-256 内容哈希、PositionedSpec 哈希、CompiledStyle 哈希和版本号。两个 Renderer
分别记录消费的 RenderIR 哈希，以此证明 HTML/PPTX 来自同一视觉快照。

RenderIR 使用固定画布坐标系。MVP 默认采用 16:9 画布，并显式保存 `canvas_width`、`canvas_height`、
`aspect_ratio`、`coordinate_unit` 和 `scale_mode=contain`。HTML 在不同视口只能整体等比缩放，不允许重新排列组件；
PPTX 使用相同画布比例和坐标换算。若后续支持 4:3，必须作为独立的画布规格和模板集合，不能在渲染时隐式拉伸。

### 9.2 文本渲染

- 标题、正文、来源分别建立文本框。
- 第一阶段可以用字符预算做快速预检，但正式布局必须由唯一的 `TextLayoutEngine` 使用固定版本字体文件和真实
  glyph metrics 计算。计算结果包括字体替换、字号、行距、显式换行点和每行边界，并冻结到 RenderIR。
- HTML 和 PPTX Renderer 只能消费 RenderIR 中已经计算好的文本布局，不能分别重新决定换行或字号。隔离
  measurement DOM、PowerPoint 转图和 LibreOffice 回归只作为校验器，用于发现运行时差异，不能成为第二套排版权威。
- 直接借鉴 `pptx-renderer/TextRenderer.ts` 的七级样式继承、段落间距、绝对/比例行距和隐藏测量根节点算法，
  但输出必须收敛为上述统一 TextLayout 结果。
- 中文排版增加 CJK 禁则、标点挤压、长数字不可拆分、中英文混排和字体 fallback 后重新测量。
- 溢出处理顺序：缩小非关键间距 -> 字号在允许范围内回退 -> fallback 模板 -> 分页。
- 禁止通过删字、改写数字或让 AI 重写来解决溢出。
- 字体缺失时按可配置 fallback chain 替换，并写入 RenderDiagnostics。
- 所有字体文件必须记录家族名、版本、许可证和 SHA-256；同一 RenderIR 禁止在不同 Renderer 中解析到不同字体文件。

### 9.3 Shape 与装饰

- 形状填充、边框、圆角、阴影均来自 ComponentSkin 白名单。
- 装饰线和色块不承载事实，不进入 FactBinding，但必须位于组件层下方且不能遮挡正文。
- 不直接复制历史 PPT 图片、Logo 或业务图形；品牌资产后续通过审核资源 ID 单独接入。

## 10. AI、Molly 与 Harness 边界

本阶段不新增 Molly 输出字段。Molly 仍只输出：

- purpose
- layout_token / archetype preference
- component_type
- claim_ids
- priority
- character_budget
- allow_pagination

Harness 继续负责超时、重试、Schema 校验和 Mock/Live 切换。TemplateCompiler、ComponentSkin 选择和 Renderer
全部由后端确定性代码完成，Molly 无权输出颜色、字体、坐标、HTML、CSS 或 PPTX。

## 11. 数据库与 API

R1-R2 可以暂不新增表，继续使用 `VisualStyleProfile.visual_json` 验证 Schema 与编译算法，但进入企业联调前
必须将“用户确认过的模板版本”和“实际渲染快照”变成不可变审计对象。

第一阶段 `visual_json` 增加：

```text
schema_version: style-profile-v2
feature_summary
design_tokens
component_skins
layout_archetypes
confidence_report
compiler_version
```

旧 v1 profile 通过适配器补默认 skin 和系统 archetype，保证历史数据可用。确认后的 StyleProfile 仍不可原地覆盖，
修改时创建新版本并保留旧 Presentation 的快照。

企业联调前新增：

```text
StyleTemplateVersion
  style_profile_id / version / status
  source_deck_hashes
  feature_set_hash / compiled_template_hash
  compiler_version / confirmed_by / confirmed_at
  compiled_template_json / confidence_report

PresentationRenderSnapshot
  presentation_id / version
  fact_ledger_snapshot_id / fact_ledger_hash
  claim_version_map / evidence_snapshot_hash / source_snapshot_hash / permission_snapshot_at
  positioned_spec_hash / compiled_style_hash / render_ir_hash
  render_ir_json / renderer_versions
  font_substitution_report / diagnostics / artifact_hashes
```

这两类记录可以独立建表，也可以先落在已有版本化 Artifact 表中；无论物理实现如何，业务上必须不可变、可追踪、
可回滚。只保存最终 HTML/PPTX 文件路径不满足企业审计要求。

API 保持现有生成路由，并补充候选模板确认能力：

```text
GET  /style-profiles/{id}/template-candidates
POST /style-profiles/{id}/template-candidates/{candidate_id}/confirm
POST /style-profiles/{id}/template-candidates/regenerate-preview
```

候选模板必须先生成脱敏示例内容预览；用户确认后才允许生成正式客户方案。`GET /style-profiles/{id}` 增量返回
`schema_version`、`confidence_report`、`confirmed_template_version` 和预览图。

候选模板采用显式状态机：

```text
draft -> previewing -> needs_review -> confirmed
                           |              |
                           -> rejected    -> superseded
任意处理阶段异常 -> failed
```

只有 `confirmed` 版本可以进入正式生成。确认操作必须校验 workspace、操作者权限、`Idempotency-Key` 和
`expected_version` 乐观锁；确认后的版本不可原地修改，重新编译或重新确认必须创建新版本。

每个候选模板不能只使用一份理想示例预览。进入 `needs_review` 前必须使用脱敏的最小、常规、最大三档内容预算进行
容量测试，并覆盖中文长句、不可拆分长数字、多来源脚注、最少/最多组件、缺失图片和字体回退。任一档出现溢出、
越界、低于最小字号或不可确定分页时，候选项不能被确认。

## 12. 分阶段实施

### R1：Golden 基线与验收门禁

- test1/test2/test3 作为第一批本地冒烟样本，不提交含业务数据的原 PPT。
- 企业联调前扩展到 30-50 套脱敏参考稿、100-200 张 Golden 页面，覆盖快消、汽车、金融、医疗、政企等
  不同行业以及封面、章节、指标、对比、时间线、流程、证据和来源页面。
- 提交脱敏 StyleFeatureSet fixture、目标 StyleProfile 和安全示例 PositionedSpec。
- 扩展现有脚本，输出 HTML/PPTX、PowerPoint PNG 和结构化 diagnostics。
- 建立人工评分表：风格相似、层级、留白、可读性、客户可展示性。

验收：基线可重复，所有失败都有截图和机器可读原因。

### R2：StyleProfile v2 与 TemplateCompiler

- 将字符串 grammar 替换为强类型 FeatureSet 与 LayoutArchetype。
- 实现坐标归一化、布局聚类、置信度和 fallback。
- 每个 archetype 生成 1-3 个候选模板和脱敏预览，只有用户确认的候选项进入 ProfileScoped LayoutRegistry。
- 候选模板在人工确认前完成三档内容预算、CJK 长文本、长数字和多来源脚注容量测试。
- 记录候选来源、匹配分数、异常页剔除原因和人工选择结果，后续可用于改进聚类算法。

验收：三个样本至少产生两种不同 archetype；同一输入重复编译结果完全一致。

### R3：ComponentSkin 与文本排版

- 先冻结 RenderIR v1，再移植开源 TextRenderer/ShapeRenderer 中可复用算法。
- 实现唯一的 TextLayoutEngine，将字体回退、字号、行距、显式换行和行框冻结到 RenderIR。
- 标题、正文、来源拆框；补 padding、边框和对齐；两个 Renderer 禁止重新计算文本布局。
- HTML 与 PPTX 使用同一 token 映射测试。

验收：当前三张测试图中的超大标题、垂直居中正文和空卡片问题全部消失。

### R4：业务模板覆盖

## 22. 2026-08-11 视觉质量复盘后的实现路线调整

当前 HTML v2 达到安全和确定性要求，但没有达到直接展示质量。根因是中间层只保留少量颜色、字体和矩形 archetype，而不是 Renderer 本身不能工作。

后续主线调整为：历史 PPTX 脱敏视觉骨架 -> 受限 Template Element Tree -> FactBinding SlidePlan 填充 -> Schema/证据校验 -> 成熟 HTML/PPTX Renderer。重点迁移 Presenton Template v2 的 Position、Size、Padding、Font、Fill、Stroke、Shadow、Container、Flex、Grid、Vector 和受限 JSON Renderer 思路；不迁移自由 Layout Code、自由文本生成和外部资源下载。

现有 RenderIR/EvidenceGuard 继续作为可信执行边界。成熟 Renderer 只能改善视觉执行，不能获得事实改写权。
