## 维护规则

本文件是 V1 集成验收阶段唯一的缺陷清单。后续三位协作者发现、修复或回归问题时，直接更新本文件，不另建同名或平行清单。

- 编号：使用连续编号 `BUG-V1-001`、`BUG-V1-002`。
- 状态：`待定位`、`修复中`、`待回归`、`已关闭`、`暂缓`。
- 严重程度：`S0` 数据或安全事故；`S1` 阻断主流程或验收；`S2` 功能可绕过；`S3` 展示或低风险问题。
- 关闭条件：必须填写修复提交、验证环境、回归步骤和结果；只有“代码已提交”不能关闭。
- 契约要求：修复不得破坏冻结 `openapi.yaml` 或 `app/contracts/ai.py` 五个方法签名；需要新接口时先补 V1 增量契约和模块 PRD。

### BUG-V1-001：飞书资料同步后无法流转到经验库或能力库

| 字段 | 内容 |
|---|---|
| 状态 | 待定位 |
| 严重程度 | S1（阻断资料沉淀主流程和 V1 飞书验收） |
| 发现日期 | 2026-08-09 |
| 发现环境 | 阿里云 `http://8.218.59.190/` |
| 代码基线 | `70d8785`，分支 `feat/v1-integration-acceptance` |
| 运行模式 | 飞书 Live；AI Mock |
| 发现方式 | 用户真实飞书联调验收 |
| 负责人 | 待分配 |

现象：飞书文档可以同步并出现在“资料库”，但后续无法流转到“过去的经验库”或“PRD 原子能力库”，也没有可完成同等结果的直接导入入口。

复现步骤：

1. 使用邀请码和飞书 OAuth 登录云端系统。
2. 点击“同步资料”，选择当前账号有权限的飞书文档。
3. 将资料用途选择为“经验提取”或“能力拆分”，执行同步与处理。
4. 在资料库确认来源已经出现或同步成功。
5. 查看经验库或能力库，无法获得对应的待校验资产，且资料详情中没有可继续完成流转的操作。

期望结果：

- `experience` 用途的资料处理后生成待校验经验，只进入经验库审核流程。
- `capability` 用途的资料处理后生成待校验原子能力，只进入能力库审核流程。
- 处理状态、失败原因和重试入口对用户可见。
- 在人工审核通过前，资产不得参与在线召回。

实际结果：资料同步入口可用，但资料库到经验库/能力库的业务流转不可完成。

影响范围：

- 阻断飞书资料沉淀为企业经验和原子能力。
- 阻断快速方案与 Deep Research 使用真实、已校验企业资产。
- 当前只能证明飞书登录、资料枚举和来源同步可用，不能据此判定资料沉淀闭环通过。

定位检查项：

- Source 创建时的 `purpose` 是否正确保存为 `experience` 或 `capability`。
- Source Job 是否创建并进入 `fetching → parsing → extracting → pending_review/completed`。
- `JobRunner` 是否实际调用 `extract_experience` 或 `extract_capabilities`。
- AI Mock 返回值能否通过 Harness Schema 与 payload adapter 校验。
- Repository 是否落库 Experience/Capability 草稿，并保持正确 `workspace_id`、来源版本和审核状态。
- 前端是否在处理完成后刷新资料、经验和能力三个列表，并显示失败与重试入口。

验收用例：同一份测试文档分别以“经验提取”和“能力拆分”导入；确认两个独立资产库各出现正确的待校验草稿，审核通过后才可被对应检索召回，同时检索快照保留来源引用。

| 发现方式 | Deep Research → 专家协作真实页面验收 |
| 负责人 | 待分配 |

现象：研究任务进入 `waiting_expert` 后，系统明确提示“暂无可推荐专家”，但“确认专家并创建飞书群”按钮仍处于可点击状态。

本轮边界：为避免产生外部副作用，本轮没有点击该按钮，未验证后端是否具备二次拦截。

### BUG-V1-005：专家群名称与首条机器人消息缺少业务化研究摘要

| 字段 | 内容 |
|---|---|
| 状态 | 待定位 |
| 严重程度 | S2（飞书联动可执行，但不满足正式协作体验） |
| 发现日期 | 2026-08-09 |
| 发现环境 | 代码核对与产品验收口径确认 |
| 代码基线 | `0d8a1f2`，分支 `feat/v1-integration-acceptance` |
| 负责人 | 待分配 |

现状：后端已经按“创建研究文档 → 创建群聊 → 发送研究卡片 → 发送开场问题”执行，但默认群名为 `淘到宝专家协作-{研究标题}`；首条内容主要是研究任务 ID、待确认问题和研究文档链接，缺少客户名称、研究背景、阶段结论、证据摘要、风险与可信边界的业务化概述。

确认的期望：

- 群名从同一份 Deep Research 上下文生成，建议格式为 `【淘到宝】与{客户名称}的{研究主题}协作`。
- 机器人第一条消息先说明“为什么建群”，并给出客户、研究问题、当前阶段结论、已确认企业依据、知识缺口、主要风险和待确认问题的简明概述。
- 第一条消息必须附同一研究任务生成的飞书研究文档链接；群聊、研究文档、问题和证据快照使用同一个 `research_task_id`。
- 机器人明确说明专家回复属于 `pending_confirmation`，不会自动成为已校验经验。
- 只有员工确认的真实作者、贡献者或审核人才能进入正式专家群；“机器人＋发起人”群仅用于接口联调，不替代正式专家协作验收。

建议首条消息结构：

1. 协作发起说明与客户名称。
2. Deep Research 问题及当前研究阶段。
3. 当前结论与企业依据摘要。
4. 知识缺口、风险和待确认问题。
5. 飞书研究文档链接。
6. 回复使用方式与可信边界说明。
