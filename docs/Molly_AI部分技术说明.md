## 1. 一句话说明我做了什么

我负责的是项目里的 **AI 引擎**：把会议纪要和企业资料变成结构化信息，根据客户问题组织检索条件，再用企业已有经验与能力生成带出处的售前方案，并通过独立质检减少大模型编造内容的风险。

可以把整个项目想成一辆车：队友负责页面、接口、数据库和飞书接入，我负责车里的“AI 大脑”。

## 2. AI 部分的完整工作流程

```text
会议纪要 / 产品文档 / 历史案例
            ↓
AI 结构化提取
客户画像 / 经验卡 / 原子能力卡
            ↓
人工审核后入库，并生成 Embedding 向量
            ↓
销售输入客户需求
            ↓
AI 提取搜索意图
            ↓
后端从经验库和能力库召回候选资料
            ↓
固化本次检索快照 RetrievalSnapshot
            ↓
AI 生成带证据边界和来源引用的方案
            ↓
独立 AI 逐条质检，不通过则最多重写两次
            ↓
输出可审核、可追问、可追溯的售前报告
```

其中，**AI 负责理解、提取、生成和质检；后端负责保存数据库、执行检索、控制权限以及真正调用飞书接口。**

## 3. 实际使用的技术

### 3.1 Python 3.11+

AI 服务使用 Python 开发。原因是 Python 适合快速调用大模型、处理 JSON、编写 AI 工作流和自动化测试，也便于后续接入更多模型或检索组件。

对应代码：`app/ai/`。

### 3.2 阿里云百炼大模型（Qwen）

项目通过阿里云百炼北京地域的 OpenAI 兼容接口调用通义千问，默认模型为 `qwen-plus`。

具体用途：

- 从会议内容中提取客户画像；
- 从历史案例中提取经验卡；
- 从产品文档中拆出原子能力卡；
- 把客户自然语言转成搜索意图；
- 生成售前方案；
- 对方案逐条做证据质检和修订；
- 生成 Memory 更新建议、Deep Research 阶段结果和专家路由结果。

工程处理包括：超时、有限重试、错误分类、JSON 输出约束、一次结构修复，以及模型和 Prompt 版本记录。

对应代码：`app/ai/model_client.py`、`app/ai/engine.py`。

### 3.3 Prompt Engineering（提示词工程）

不同任务使用不同 Prompt，而不是用一个万能提示词处理所有事情。目前按任务拆分了画像、经验、能力、搜索意图、方案生成、质检、重写、Memory、深度研究和专家路由等 Prompt。

这样做的价值：

- 每个模型调用只有一个清晰任务；
- 输出格式更稳定；
- 便于单独调试和版本管理；
- 可以限制模型只根据给定证据回答。

对应代码：`app/ai/prompts/`。

### 3.4 Pydantic 结构化输出与严格校验

大模型不能只返回一段随意文字，它必须返回规定好的 JSON。Pydantic 相当于“标准表格检查员”：字段缺失、类型错误、引用不合法或上下文不完整时，结果不能直接进入下游。

主要数据结构包括：

- `CustomerProfileDraft`：客户画像草稿；
- `ExperienceDraft`：历史经验卡；
- `CapabilityDraft`：原子能力卡；
- `SearchIntent`：搜索意图；
- `RetrievalSnapshot`：本次生成所依据的资料快照；
- `Solution`：带引用的方案；
- `QualityReport`：逐条质检结果；
- `ProfileMemoryProposal`：待人工确认的画像更新建议。

对应代码：`app/ai/schemas/`。

### 3.5 Embedding（文本向量化）

Embedding 会把一段文字变成一串数字，使计算机可以比较两段文字“意思有多像”。项目使用百炼 `text-embedding-v4`，默认向量维度为 1024，并通过余弦相似度比较语义相似度。

已实现的工程能力：

- 单条和批量向量化；
- 文本清洗和长度限制；
- 向量维度校验；
- 内容 SHA-256 指纹；
- 超时、重试和错误处理；
- Mock Embedding，支持离线联调。

Embedding 是检索的工具，不是一个单独对外暴露的 AI 业务接口。

对应代码：`app/ai/embedding.py`。

### 3.6 RAG（检索增强生成）的 AI 侧能力

RAG 可以理解为：**先从企业自己的资料中找证据，再让 AI 根据证据写答案。** 它不是让模型凭记忆自由发挥。

本项目 AI 侧已经完成：

- 将用户问题转成经验库查询词和能力库查询词；
- 定义检索结果的严格结构；
- 只允许引用本次检索快照中的资产；
- 区分历史事实、企业能力、AI 推断和待客户确认内容；
- 资料不足时允许明确回答“当前知识库证据不足”。

数据库查询、Top-K 召回、审核状态过滤以及向量持久化由后端负责，需在集成分支中与队友完成联调。

对应代码：`app/ai/pipelines/search_intent.py`、`app/ai/schemas/retrieval.py`、`app/ai/pipelines/solution.py`。

### 3.7 可信引用与防幻觉机制

方案中的每条内容被划分为四类：

1. `historical_fact`：历史案例事实，必须带资产 ID 和来源 ID；
2. `enterprise_capability`：企业现有能力，必须带资产 ID 和来源 ID；
3. `ai_inference`：AI 推断，不能冒充企业事实；
4. `pending_confirmation`：需要客户或顾问继续确认的信息。

代码会检查：

- 引用的资产是否真的在本次检索结果中；
- 经验是否被标成历史事实、能力是否被标成企业能力；
- 所有引用是否出现在来源清单里；
- 没有证据的推断是否错误绑定了企业来源。

这使“报告有出处”不只是一句 Prompt，而是可由代码验收的规则。

### 3.8 独立 Critic 质检与自动重写闭环

第一轮模型负责写方案，另一轮独立模型扮演质检员，把方案拆成一条条论断，再逐条对照证据。

如果有论断不受支持，系统将质检原因交给修订流程重新生成，最多重写两次。每次原方案、质检报告和修改次数都会保留，最后输出是否通过。

对应代码：

- 生成：`app/ai/pipelines/solution.py`；
- 质检：`app/ai/pipelines/quality.py`；
- 修订：`app/ai/pipelines/revision.py`；
- 闭环：`app/ai/pipelines/workflow.py`。

### 3.9 Memory（客户画像记忆）

Memory 不是让 AI 偷偷记住所有聊天，而是：AI 从新会话中提出“画像应该怎样更新”的建议，标记来源，并等待人工确认。只有用户或顾问确认后，后端才能正式更新客户画像。

这种设计可以避免一次误解永久污染客户资料。

对应代码：`app/ai/pipelines/memory.py`、`app/ai/schemas/memory.py`。

### 3.10 Deep Research 与专家路由

项目为后续复杂售前问题预留了深度研究模式：把大问题拆成研究计划和子问题，记录研究发现、证据边界与审计结果；当内部资料不足时，可以根据真实候选人信息生成专家推荐和待提问问题。

这里的专家候选必须来自后端提供的真实名单，AI 只能排序和解释原因，不能编造一个不存在的专家。

对应代码：`app/ai/pipelines/deep_research.py`、`app/ai/pipelines/expert_routing.py`、`app/ai/schemas/research.py`。

### 3.11 飞书协作内容模板

AI 侧可以把已经生成并校验过的结果整理为：

- 飞书文档草稿；
- 飞书消息卡片草稿；
- 专家协作群开场内容；
- 专家回复摘要。

AI 侧只生成内容结构，真正创建飞书文档、发送卡片和建群由队友负责的飞书集成层执行。

对应代码：`app/ai/collaboration.py`、`app/ai/schemas/collaboration.py`。

### 3.12 Mock、自动化测试与离线评测

项目提供真实百炼实现和 Mock 实现。Mock 像“练习模式”，不联网、不花模型费用，队友仍可先完成接口联调和回归测试。

测试与评测包括：

- Schema 和边界规则测试；
- 大模型客户端、重试和错误测试；
- Embedding 测试；
- 提取、搜索意图和方案生成测试；
- 质检—修订闭环测试；
- Memory、Deep Research、专家路由测试；
- CLI 和 Golden 示例测试；
- 业务评测集，检查引用支持度、边界正确性和预期资产命中。

对应代码：`tests/ai/`、`app/ai/evaluation.py`、`evals/`、`examples/golden_a3/`。

开发阶段曾完成全项目 `98 passed`；后续两个分支合并后仍需重新运行完整测试和真实百炼联调。

## 4. 对外提供的五个 AI 接口

| 接口 | 输入 | 输出 | 用途 |
| --- | --- | --- | --- |
| `extract_profile` | 会议文字、来源 ID | 客户画像草稿 | 沉淀客户背景、问题、目标和信息缺口 |
| `extract_experience` | 案例文字、来源 ID | 经验卡 | 把历史项目变成可搜索资产 |
| `extract_capabilities` | 产品文字、来源 ID | 原子能力卡列表 | 把长文档拆成细粒度能力 |
| `extract_search_intent` | 当前客户和会话上下文 | 搜索意图 | 指导后端检索经验库和能力库 |
| `generate_solution` | 客户上下文、检索快照 | 结构化方案 | 生成带证据边界和来源的报告 |

接口协议位于 `app/contracts/ai.py`。队友不需要理解 Prompt 内部，只需要按照约定的数据格式调用这五个方法。

## 6. 目前明确没有使用的技术

为了保证技术说明真实，当前代码 **没有实际使用**：

- LangGraph；
- Neo4j；
- GraphRAG；
- 自训练或微调模型；
- 自建 ASR 语音识别；
- 自建向量数据库。

当前工作流由 Python 代码显式编排；知识检索采用“结构化检索契约 + Embedding”的方案。以后如果资产规模和关系复杂度明显增加，再评估引入向量数据库、GraphRAG 或 LangGraph，而不是为了技术名词提前增加复杂度。

## 8. 答辩时可以这样介绍技术亮点

> 我负责项目的 AI 引擎。它不是让大模型直接凭空写一份方案，而是先把企业案例和能力文档结构化，通过 Embedding 和后端检索取得证据快照，再生成逐条带来源的方案。我们用 Pydantic 把输出格式和引用规则写成可校验的代码，并让独立 Critic 对每条论断回查证据，不通过时最多修订两轮。客户画像更新也不是 AI 自动覆盖，而是先生成带来源的 Memory 建议，再由人确认。这使 AI 输出从“看起来合理”变成“有出处、可检查、可追踪”。

## 10. 使用边界

- 真实 API Key 只能保存在本地 `.env`，不能上传 GitHub；
- AI 不直接读取业务数据库，也不持有飞书 Token；
- AI 生成的是待审核材料，不替代顾问最终判断；
- 未经人工确认，AI 不能修改客户画像、审核资产或执行外部操作；
- RAG 的后端召回效果需要在双方代码合并后用真实数据继续验证。
