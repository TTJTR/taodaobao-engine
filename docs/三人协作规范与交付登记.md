# 淘到宝引擎三人协作规范与交付登记

文档定位：项目协作与交付的总入口

维护人员：项目负责人、开发 A、开发 B

适用范围：淘到宝引擎 V0.5、V1 及后续迭代

## 0. 文档使用原则

本文件由三名成员共同维护，但不同部分的维护权限不同：

| 部分 | 内容所有人 | 维护规则 |
|---|---|---|
| 第一部分：协作规范与流程 | 项目负责人 | 由项目负责人定义和最终确认；其他成员可以提出修改建议，但不能自行改变规则 |
| 第二部分：当前版本与公共基线 | 项目负责人 | 项目负责人根据已合并、已验收结果更新 |
| 第三部分：成员交付登记 | 对应交付负责人 | 每位成员负责填写和更新自己的交付；审核人检查真实性和完整性 |
| 第四部分：公共决策与问题 | 三人共同维护 | 谁提出谁记录，相关成员确认，重大决定由项目负责人最终确认 |
| 第五部分：变更记录 | 实际修改人 | 每次修改本文件都要追加记录，不能删除历史记录 |

本文件不是工作周报，也不是把所有开发细节堆在一起。它只记录：

- 三个人共同遵守的规则；
- 当前唯一有效的开发基线；
- 每个人已经完成并可验证的交付；
- 尚未完成、存在风险或需要共同决定的事项；
- 规则和关键决定的变更历史。

详细日常操作见：

- [合作伙伴代码更新操作手册（GitHub 网页版）](合作伙伴代码更新操作手册.md)
- [协作开发与 Git 提交规范](协作开发与Git提交规范.md)

# 第一部分：协作规范与流程

> 本部分由项目负责人定义。任何规则变化必须由项目负责人确认，并在“规则变更记录”中留下原因、生效时间和影响范围。

## 1. 三人角色与职责

请项目负责人补充三人的真实姓名或 GitHub 用户名：

| 角色 | 姓名/GitHub | 主要职责 | 最终确认范围 |
|---|---|---|---|
| 项目负责人 | 待填写 | 产品范围、优先级、协作规则、验收结论、发布决定 | 需求、规则、验收、是否进入 `main` |
| 开发 A | 待填写 | 后端、数据库、飞书集成、任务编排、部署 | 对应模块实现和测试证据 |
| 开发 B | 待填写 | AI Schema、Prompt、算子、评测和可信边界 | 对应模块实现和测试证据 |

职责边界可以调整，但必须先在本表更新并由项目负责人确认。任何成员都不能因为“顺手”而静默修改其他成员负责的核心模块。

## 2. 唯一协作渠道

| 内容 | 唯一正式渠道 |
|---|---|
| 代码、分支、提交和版本 | GitHub 私有仓库 |
| 代码审核和合并 | GitHub Pull Request |
| 需求、任务和产品决定 | 飞书文档或指定飞书群 |
| 协作规范与交付状态 | 本文件 |
| 密钥和生产凭证 | 服务器环境变量或受控密钥管理工具 |

不得使用压缩包互相覆盖代码。飞书或微信中发送的代码片段只能用于讨论，最终结果必须进入 GitHub。

## 3. 分支规则

| 分支 | 用途 | 规则 |
|---|---|---|
| `main` | 已验收、可部署的稳定版本 | 禁止直接开发和直接 Push |
| `v1-integration` | V1 日常集成、联调和验收 | 只通过 Pull Request 合并 |
| `feat/*` | 新功能 | 一个任务一个分支 |
| `fix/*` | 缺陷修复 | 一个问题一个分支 |
| `docs/*` | 独立文档更新 | 不混入无关业务代码 |

当前过渡规则：在 `v1-integration` 正式建立并包含当前集成代码之前，新任务从 `feat/v1-integration-acceptance` 创建分支。建立 `v1-integration` 后，所有新任务统一从 `v1-integration` 创建。

禁止事项：

- 不得直接在 `main` 修改代码；
- 不得从旧分支开始新任务；
- 不得在一个分支混合多个无关任务；
- 不得删除或覆盖其他成员未合并的成果；
- 不得在服务器上临时修改代码而不回写 GitHub。

## 5. Codex 最小上下文规则

考虑到三个人的 Codex 额度不同，不要求任何成员每次完整读取整个仓库。

每项任务只提供一个最小上下文包：

1. 一页任务说明；
2. 当前开发基线和目标分支；
3. 3～8 个必须读取的实现、测试和契约文件；
4. 允许修改范围；
5. 禁止修改范围；
6. 测试命令和验收标准。

给 Codex 的固定要求：

```text
不要扫描或完整读取整个仓库。
先完整读取任务清单中列出的文件。
只有确实存在依赖时才通过 rg 定位额外文件。
读取额外文件前先说明依赖关系。
不要进行与任务无关的架构分析或重构。
```

一个独立任务使用一个 Codex 对话，避免把多个模块长期堆在同一个对话中。

## 6. 开发与提交规范

1. 开发前检查当前分支和工作树。
2. 优先复用现有结构，不做无关重构。
3. Mock 必须与真实接口使用相同 Schema，并明确标识。
4. 不使用写死结果伪装完成接口。
5. 每完成一个独立、可验证的小功能提交一次。
6. 只提交属于本任务的文件。
7. 提交信息采用：

```text
<类型>(<模块>): <具体修改>
```

示例：

```text
feat(feishu): add tenant token provider
fix(ai): normalize experience evidence status
test(research): cover expert reply resume
docs(deployment): add cloud setup guide
```

## 7. 冻结契约规则

### 7.1 HTTP 契约

- 前端与后端的冻结契约是 `openapi.yaml`。
- 不得擅自修改已有路径、字段语义和状态枚举。
- V1 新接口通过增量契约新增，并同步模块 PRD。

### 7.2 AI 契约

后端与 AI 服务保持五个冻结方法签名：

- `extract_profile`
- `extract_experience`
- `extract_capabilities`
- `extract_search_intent`
- `generate_solution`

Embedding 是共享适配能力，不增加第六个冻结方法。

### 7.3 契约变更流程

任何成员认为必须修改共享契约时：

1. 先在飞书说明原因、字段变化和影响范围；
2. 由另外两名成员查看；
3. 项目负责人确认产品语义；
4. 同一个 PR 中包含增量契约、实现、测试和文档；
5. 未确认前不得静默修改。

## 8. 测试与验收规范

通用检查：

```bash
git status --short
git diff --check
uv run --extra dev pytest -q
uv run --extra dev ruff check app tests
```

模块验收：

| 模块 | 最低验收要求 |
|---|---|
| AI | 单元测试、Mock 回归、黄金案例、引用、拒答和可信边界 |
| 后端 API | 路由、响应 Schema、错误码、幂等性和冻结契约检查 |
| 数据库 | Alembic 迁移、约束、升级路径、数据保留和回滚风险 |
| 飞书 | 测试企业登录、权限、文档、妙记、机器人、回调和失败恢复 |
| 前端 | 页面加载、主要操作、接口错误态和真实浏览器验证 |
| 部署 | Docker 构建、迁移、HTTPS、健康检查、持久化和重启恢复 |

测试失败时不能登记为“已完成”。必须写明失败命令、错误、影响范围和下一步负责人。

## 9. Pull Request 规范

所有功能和缺陷修复都通过 GitHub 网页创建 Pull Request。

PR 必须包含：

- 任务目标和实现范围；
- 修改文件；
- 上游依赖和下游影响；
- 契约、数据库和环境变量变化；
- 测试命令和真实结果；
- 未完成项、风险和回滚方式；
- 本文件中的交付登记更新。

每个 PR 至少由另一名成员审核。涉及产品语义、冻结契约或是否发布时，必须由项目负责人确认。

审核人必须检查：

- 是否符合已确认需求；
- 是否混入无关修改；
- 是否破坏冻结契约；
- 是否包含真实密钥或客户资料；
- 测试证据是否可信；
- 交付登记是否完整。

## 10. 合并与发布流程

日常功能：

```text
个人功能分支
  → Pull Request
  → 审核与测试
  → v1-integration
```

正式发布：

```text
v1-integration
  → V1 端到端验收
  → 发布 Pull Request
  → main
  → 使用 main 的提交或版本标签部署
```

只有以下条件全部满足，项目负责人才能确认进入 `main`：

1. 产品确认发布范围；
2. 前端、后端、AI 和数据库集成测试通过；
3. 真实飞书登录、权限、资料读取、机器人和回调通过；
4. 云端部署、迁移、HTTPS、持久化和重启恢复通过；
5. 没有高优先级阻断缺陷；
6. 验收报告、部署说明、交付登记和回滚方式已更新。

## 11. 安全规范

绝对不能提交：

- `.env`；
- 百炼 API Key；
- 飞书 App Secret、访问 Token 和 Cookie；
- 数据库密码；
- 真实客户资料、内部文档正文和个人信息；
- 本地数据库、缓存、日志和虚拟环境。

密钥进入 GitHub、PR 或聊天记录后，必须立即撤销旧密钥并生成新密钥，不能只删除文本。

## 12. 冲突与阻塞处理

1. 开工前声明任务、分支和预计修改文件。
2. 尽量避免两人同时修改同一个核心文件。
3. 出现冲突时逐段确认双方逻辑，不允许整文件覆盖。
4. 不熟悉冲突处理时保留现场，将 PR、`git status` 和冲突文件发给负责人。
5. 同一阻塞持续存在时，在“公共问题登记”中记录负责人和下一步。

以下文件冲突时必须共同评审：

```text
openapi.yaml
docs/openapi-v1-incremental.yaml
AI 五个冻结方法对应契约
app/db/models.py
alembic/versions/*
pyproject.toml
```

# 第三部分：成员交付登记

> 每位成员维护自己的交付记录。交付必须能够通过分支、Commit、PR、测试或文档链接复现。没有证据的内容不能登记为“已完成”。

## 16. 交付状态定义

| 状态 | 含义 |
|---|---|
| `planning` | 已确认任务，尚未开始实现 |
| `developing` | 开发中，尚未达到提交验收条件 |
| `reviewing` | 已创建 PR，等待审核或修改 |
| `accepted` | 已通过对应范围验收，但不一定进入正式发布 |
| `merged` | 已合并到集成分支 |
| `released` | 已进入 `main` 并完成部署 |
| `blocked` | 存在明确外部阻塞，已记录负责人和下一步 |

## 17. 交付登记规则

每项交付必须包含：

- 唯一交付 ID；
- 负责人；
- 对应任务和模块；
- 分支、Commit 和 PR；
- 具体实现；
- 修改文件或目录；
- 契约、数据库和环境变量影响；
- 测试命令与真实结果；
- 未完成项和风险；
- 当前状态和更新时间。

成员只能修改自己的交付事实。需要更正其他成员记录时，应在 PR 评论中提出，由原负责人或项目负责人修改。历史交付不得直接删除；作废时标记 `superseded` 并链接替代交付。
