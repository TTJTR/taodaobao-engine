## 2. 调研目标

本调研回答以下问题：

1. 成熟系统如何采集、清洗、去重和版本化公开情报。
2. 如何解析 PDF、DOCX、XLSX、PPTX，并使要求可回到原文位置。
3. 企业 RFP/招标响应系统如何组织证据、答案、负责人、审核和版本。
4. 哪些开源能力可以复用，哪些业务能力必须由本项目确定性实现。
5. 如何在不破坏 V1/V1.1 冻结契约的前提下落地 V2。

调研结论是：本模块不应采用“搜索结果直接交给 LLM，再生成整份答案”的 Demo 架构。成熟实现普遍采用“数据供应链、不可变来源、结构化业务资产、人工审批工作流”，AI 只负责提取、匹配和起草。

## 3. 参考项目与可借鉴能力

### 3.1 Open Contracting Data Standard

- 项目：<https://standard.open-contracting.org/latest/en/>
- 代码：<https://github.com/open-contracting/standard>
- 主要思想：采购过程中的每次变化以独立 `release` 表示，再聚合为当前完整 `record`。
- 可借鉴点：
  - 新采集或修订产生新版本，不覆盖历史事实。
  - 当前聚合视图与历史发布记录分离。
  - 采购主体、阶段、文档和变更具有明确语义。
- 本项目映射：`IntelligenceItem` 当前视图、`IntelligenceSnapshot` 历史快照、`TenderParseVersion` 和 `RequirementVersion`。

本项目不需要完整实现 OCDS，但应采用其“变化记录不可变、当前视图可重建”的版本思想。

### 3.2 Kingfisher Collect 与 Kingfisher Process

- 采集：<https://github.com/open-contracting/kingfisher-collect>
- 处理：<https://github.com/open-contracting/kingfisher-process>
- 主要思想：采集和处理是两条独立流水线；原始采集结果先保存，再进行加载、校验、转换和去重。
- 可借鉴点：
  - 每个数据源拥有独立执行状态和失败原因。
  - 部分来源失败不应丢弃其他来源的成功结果。
  - 原始数据和规范化数据分开存储。
- 本项目映射：`SearchRun -> SearchProviderRun -> CrawlArtifact -> IntelligenceItem`。

### 3.3 Aleph

- 项目：<https://github.com/alephdata/aleph>
- 主要思想：将文档、实体、关系、集合、权限和来源溯源分开建模，支持调查资料检索和实体关联。
- 可借鉴点：
  - 公司、人物、项目、政策和招标不是普通标签，而是可关联实体。
  - 每个结构化事实必须能够回到来源文档。
  - 一个调查集合中的权限和资产边界不可由搜索索引替代。
- 注意：该开源版本已公告停止持续维护。本项目只借鉴建模思想，不将 Aleph 整体作为运行依赖。

### 3.4 Docling

- 项目：<https://github.com/docling-project/docling>
- 格式说明：<https://docling-project.github.io/docling/usage/supported_formats/>
- 主要能力：解析 PDF、DOCX、PPTX、XLSX 等格式，提供统一 `DoclingDocument` 表示，并处理 PDF 页面布局、阅读顺序和表格结构。
- 本项目价值：最接近 P0 招标文件解析与原文定位要求，建议作为主解析器技术验证对象。
- 验证重点：
  - 中文复杂表格、合并单元格和跨页表格。
  - 扫描 PDF 与 OCR 的资源消耗和准确率。
  - DOCX 段落、XLSX 单元格、PPTX 形状的稳定定位。
  - 超大文件、异常压缩包和恶意嵌入对象的安全边界。

### 3.5 Unstructured

- 项目：<https://github.com/Unstructured-IO/unstructured>
- Partition 文档：<https://docs.unstructured.io/open-source/core-functionality/partitioning>
- 主要能力：把原始文档拆成 `Title`、`NarrativeText`、`ListItem`、`Table` 等结构化元素。
- 本项目价值：可作为 Docling 的格式补充或降级解析器，不负责最终业务要求状态。

### 3.6 MarkItDown

- 项目：<https://github.com/microsoft/markitdown>
- 主要能力：快速将 Office 文档、PDF 等转换为 Markdown。
- 适用位置：解析失败后的可读文本降级、人工预览或开发诊断。
- 不适用位置：正式要求定位。Markdown 文本通常不足以稳定表达页码、工作表、单元格、幻灯片形状和版本血缘。

### 3.7 Crawlee Python

- 项目：<https://github.com/apify/crawlee-python>
- 主要能力：HTTP/浏览器抓取、持久请求队列、并发控制、状态恢复和结构化结果存储。
- 可借鉴点：Provider 协议、持久 URL 队列、断点恢复、按来源限流和运行级存储。
- 合规限制：本项目不得使用规避登录、验证码、付费墙、robots 或其他访问控制的能力。默认优先普通 HTTP 采集；只有公开页面确实依赖 JavaScript 且合规策略允许时，才评估浏览器渲染。

## 4. 成熟公开情报流水线

推荐的数据生命周期如下：

```text
SearchRun
-> SearchProviderRun
-> CrawlArtifact
-> 安全与合规检查
-> 正文和元数据抽取
-> URL 规范化与正文指纹
-> 实体、事实、重复和冲突候选
-> 人工确认
-> IntelligenceItem
-> IntelligenceSnapshot
```

### 4.1 原始采集与业务资产分离

`CrawlArtifact` 是不可变原始采集记录，至少保存：

- 原始 URL 与规范 URL。
- Provider、运行 ID、HTTP 状态和采集时间。
- MIME、字符集、内容哈希和提取器版本。
- 公开发布时间及其解析依据。
- 安全检查、合规检查和错误码。
- 原文存储引用；日志中不保存完整敏感正文。

`IntelligenceItem` 是经过规范化和审核的业务对象。抓取成功不代表情报有效，也不能直接写入画像或方案快照。

### 4.2 多层去重

去重顺序建议为：

1. URL 规范化：去除跟踪参数、规范域名和路径。
2. 精确正文指纹：识别镜像页、转载页和同内容更新。
3. 结构化事实比较：判断同一主体、事件和时间。
4. 语义相似度：只生成“可能重复”建议。
5. 人工或确定性规则决定主条目和关联来源。

AI 不得直接物理删除重复项。一个 `IntelligenceItem` 应允许关联多个来源，以保留交叉验证能力。

### 4.3 冲突与时效

冲突信息不强制合并为一个结论，可通过 `conflict_group_id` 或显式关系保存双方来源、发布时间和差异字段。

以下状态相互独立：

- 采集运行：`queued/running/completed/partial/failed/cancelled`。
- 来源可用性：`current/stale/unavailable/deleted`。
- 情报审核：`pending/accepted/rejected/superseded`。

历史快照保留当时内容；来源失效后，新快照不得继续纳入该来源，业务页面不得返回可还原的失效原文。

## 5. 招标文档解析架构

招标文件不能直接交给模型整份处理。推荐先构建统一文档中间表示：

```text
TenderDocument
-> 文件安全检查
-> TenderParseVersion
-> DocumentNode（章节、段落、表格、单元格、形状）
-> RequirementCandidate
-> 人工合并、拆分、编辑和确认
-> RequirementVersion
```

### 5.1 跨格式原文位置

建议冻结统一 `source_location` Schema：

```json
{
  "kind": "pdf_page|docx_paragraph|xlsx_cell|pptx_shape|plain_text",
  "page": 12,
  "section_path": ["第三章", "技术要求"],
  "paragraph_index": 8,
  "sheet": null,
  "cell_range": null,
  "slide": null,
  "shape_id": null,
  "text_offset": null,
  "quote_hash": "sha256:..."
}
```

页码只适用于 PDF 等固定页面格式。XLSX 应使用工作表和单元格，PPTX 应使用幻灯片和形状，DOCX 应使用章节路径和段落标识。`quote_hash` 用于发现重新解析后的原文漂移。

### 5.2 AI 与人工校正

AI 拆解输出只能创建 `RequirementCandidate`。合并、拆分、编辑和作废应创建新版本或新条目，并将旧版本标记为 `superseded`，不能覆盖或物理删除历史。

要求确认后才能用于正式响应矩阵。文件重新解析或要求版本变化时，相关响应项转为 `stale`。

## 6. 企业 RFP 响应工作流

Loopio、Responsive、Inventive 等成熟商业产品公开展示的工作流具有共同结构：

```text
机会或文件导入
-> Go/No-Go 判断
-> 问题或要求拆分
-> 分配责任人
-> 从已批准内容库推荐答案
-> 专家编写或补充
-> 审核人复核
-> 商务、法务或负责人批准
-> 冻结版本
-> 导出或进入正式方案
```

成熟实现的重点并非一次性生成整份投标文档，而是：

- 只推荐已批准且未过期的内容。
- 每项要求有负责人、审核人和截止时间。
- 编辑、退回、复核和批准是不同动作。
- 保存 AI 初稿、人工编辑和最终批准版本。
- 记录答案和证据的所有者、有效期与最近审核时间。
- 统计内容被使用、修改、退回和过期的情况。

P0 可以不实现复杂任务分派，但建议为 `ResponseItem` 预留 `owner_id`、`reviewer_id` 和 `due_at`，避免 P1 协作能力需要破坏性迁移。

## 7. 推荐响应项模型

`ResponseItem` 不应只有单一答案字段，至少需要：

| 字段 | 说明 |
|---|---|
| `requirement_id` / `requirement_version` | 固定到已确认要求版本 |
| `ai_draft` | 原始 AI 草稿，后续编辑不覆盖 |
| `current_answer` | 当前人工可编辑答案 |
| `evidence_status` | `supported` 等 PRD 冻结状态 |
| `review_status` | 草稿、接受、退回、专家确认、拒绝 |
| `risk_flags` | 价格、周期、指标、责任人、保证、合规等 |
| `information_gaps` | 缺失依据与待确认问题 |
| `owner_id` / `reviewer_id` | 责任人和审核人，可在 P0 为空 |
| `version` | 乐观并发控制和审计版本 |
| `approved_at` | 正式通过时间 |

证据关系必须分开保存：

- `ResponseItemExperienceLink`：企业历史经验。
- `ResponseItemCapabilityLink`：企业能力。
- `ResponseItemIntelligenceLink`：外部公开背景。

不得用一个无类型的 `knowledge_links` 集合混合三种来源。

## 8. 推荐总体架构

```text
公开网站 / 手工 URL / 粘贴文本 / 招标文件
                         |
                    Ingestion Layer
        合规、SSRF、文件安全、限流、重试、哈希
                         |
                    Raw Artifact Layer
                         |
              Deterministic Normalization
      URL、正文、Document IR、位置、指纹、精确去重
                         |
                  Molly AI Enrichment
       摘要、分类、事实候选、要求拆解、回答草稿
                         |
                 Business Review Layer
     情报确认、画像提议、要求校正、逐项审核、版本
                         |
                   Immutable Snapshot
                         |
             Quick Solution / Deep Research
```

代码职责继续遵循：

- Router：参数、鉴权依赖、幂等依赖和统一响应。
- Service：状态机、事务、版本、权限、AI 编排和可信规则。
- Repository：所有查询的 Workspace 隔离和软删除过滤。
- Provider：搜索、网页抽取、文档解析与 Molly 模型适配。
- Worker：长任务、租约、心跳、重试和阶段历史。

## 9. 复用与自建决策

### 9.1 建议技术验证

- Docling：P0 四类招标文件的主解析器候选。
- Unstructured：补充格式和降级解析候选。
- `httpx + trafilatura`：普通公开 HTML 的轻量抓取与正文提取候选。
- Crawlee：参考持久请求队列和断点恢复；是否直接引入取决于与现有 Worker 的重复度。
- OCDS：参考采购版本和阶段语义，不整体实现。

### 9.2 必须由本项目实现

- Workspace 鉴权和隔离。
- 情报条目、冲突、时效和快照。
- 画像字段级提议和人工确认。
- 内部经验、内部能力、外部背景的隔离。
- 要求校正、版本血缘和响应矩阵。
- 高风险审核、Trust Gate、幂等和审计。
- 与现有 `SolutionRun`、`ResearchTask`、`WorkflowTask` 的集成。

### 9.3 不建议采用

- 直接部署大型 OSINT 平台替代本项目业务模型。
- 以小型 TenderGPT/RFP Demo 作为生产基础。
- 将外部网页全文写入现有内部 `Source`。
- 只保存向量，不保存关系数据库中的来源和版本。
- 让 LLM 决定权限、来源有效性、最终去重或批准状态。
- 使用绕过验证码、登录、付费墙或网站访问控制的采集能力。

## 10. 对 V2 契约的补充建议

正式冻结增量 OpenAPI 和迁移前，建议补充：

1. 明确 `CrawlArtifact` 为不可变原始采集层。
2. `IntelligenceItem` 与来源采用一对多关系。
3. 为冲突条目增加显式关系或 `conflict_group_id`。
4. 冻结跨格式 `source_location` Schema。
5. 将解析成功、AI 拆解完成、人工要求确认定义为不同阶段。
6. 为响应项预留负责人、审核人、截止时间和批准时间。
7. 增加要求编辑、合并、拆分、确认、作废和历史查询接口。
8. 增加搜索、解析和矩阵生成的显式重试接口。
9. 快照保存必要事实和来源元数据，不能只保存可变实体 ID。
10. V2 AI 能力通过独立业务协议接入共享模型客户端，不修改冻结的五个 `AIEngine` 方法。

## 11. 风险与验证重点

- 文档解析：复杂表格、扫描 PDF、合并单元格和文本定位可能不稳定。
- 供应链：新增解析依赖应进行许可证、CVE、镜像体积和资源消耗评估。
- 采集合规：搜索供应商条款、robots、版权、个人公开职业信息和来源失效处理。
- 数据可信：语义相似不能替代来源验证，外部信息不能转为企业能力。
- 并发：要求校正和逐项审核必须使用期望版本，防止覆盖他人修改。
- 可恢复性：重试不得重复创建快照、画像版本、要求版本或响应项。
- 性能：大文件解析必须在 Worker 中运行，设置大小、页数、耗时和内存上限。
- 可观测性：除当前阶段外，还需保留每次任务的阶段历史、错误码和重试次数。

## 12. 建议落地顺序

1. 冻结数据生命周期、状态机、跨格式位置和增量 OpenAPI。
2. 对 Docling、Unstructured 和轻量网页抽取方案做隔离 PoC。
3. 实现原始采集层、规范化层和不可变快照。
4. 实现画像提议和人工确认闭环。
5. 实现招标解析、要求版本与人工校正。
6. 实现内部证据检索、响应矩阵和逐项审核。
7. 接入快速方案、Deep Research、统一 Worker 和 AI 后台观察。

每一阶段均不得修改 V1.1 演示渲染模块，并需保持现有 HTTP 契约和五个 `AIEngine` 方法签名不变。
