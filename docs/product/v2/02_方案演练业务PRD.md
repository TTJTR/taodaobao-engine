## 0. 文档信息

| 项目 | 内容 |
|---|---|
| 版本 | V2.0 |
| 文档状态 | 产品确认稿，待技术评审 |
| 更新日期 | 2026-08-11 |

## 1. 产品定义

“方案演练”是基于已有客户画像和方案上下文构建的 AI 客户异议演练空间。员工通过与模拟客户进行多轮问答，提前发现方案中的证据缺口、过度承诺、表达问题和未覆盖异议。

它不是通用聊天机器人，也不是员工绩效评价系统。

产品原则：

> 模拟客户帮助员工准备真实沟通，但不能冒充真实客户意见，也不能替代员工判断。

## 2. 业务目标

- 在会议、汇报和投标答辩前进行低成本、多轮演练。
- 让演练基于真实客户画像、企业依据和最新情报，而不是随机生成问题。
- 发现方案对客户目标、角色关注点和招标要求覆盖不足的地方。
- 识别无依据承诺、证据错用和应当明确待确认的内容。
- 输出可执行的改进建议，帮助员工修订方案和准备沟通。

## 3. 范围

### 3.1 P0 必须完成

- “方案演练”一级页面。
- 从快速方案或 Deep Research 一键进入演练。
- 在演练页自主选择已有方案。
- 读取同一客户画像、方案快照、情报快照和响应矩阵。
- 配置客户角色、关注重点、难度和轮数。
- 模拟客户提出多轮异议和追问。
- 员工输入回答。
- 每轮生成结构化评价和改进建议。
- 识别证据不足、过度承诺和客户信息误用。
- 生成演练报告。
- 支持重新演练和历史记录。
- 演练任务接入 AI 后台工作台。

### 3.2 P1

- 预设行业与角色场景模板。
- 多角色轮流提问。
- 招标答辩模式。
- 会议时间限制模式。
- 两次演练报告对比。
- 从报告创建“方案修改建议”，但仍需人工确认。

### 3.3 暂不实现

- 不接管真实客户沟通。
- 不自动向客户发送消息。
- 不对员工进行绩效排名。
- 不把演练评分直接用于人事决策。
- 不把AI模拟问题声称为真实客户反馈。
- 不自动修改客户画像、经验库、能力库或正式方案。
- 不在快速方案或演练中使用 Multi-Agent。
- 不脱离 Deep Research 单独发起专家协作。

## 4. 产品入口与信息架构

### 4.1 两个入口

1. 快速方案或 Deep Research 结果页：“基于当前方案开始演练”。
2. 方案演练页：“选择一个已有方案开始演练”。

两个入口必须构建相同的 `RehearsalContext`。

### 4.2 页面结构

```text
方案演练
├─ 演练列表
├─ 新建演练
│  ├─ 选择客户和方案
│  ├─ 查看上下文
│  └─ 配置角色与难度
├─ 演练聊天室
│  ├─ 客户问题
│  ├─ 员工回答
│  └─ 每轮反馈
└─ 演练报告
   ├─ 总结
   ├─ 证据与风险
   ├─ 异议覆盖
   └─ 改进建议
```

## 5. RehearsalContext

创建演练时固化独立上下文快照，至少包含：

- `rehearsal_id`
- `customer_profile_id` 与画像版本
- `solution_run_id` 或 `research_task_id`
- 当前方案或研究报告版本
- `intelligence_snapshot_id`（可选）
- `response_matrix_id` 与版本（可选）
- 内部经验和能力检索快照
- 可信决策和已发布主张
- 知识缺口
- 待确认问题
- 创建时间和创建人

规则：

- 只读取通过现有权限检查的内容。
- 上游资产变化不能篡改已经开始的演练。
- `REVIEW` 或 `BLOCK` 的方案不能被包装成正式可靠结论；页面必须显示上游状态。
- 外部情报与企业依据分开展示。

## 6. 新建演练

### 6.1 选择上游方案

列表字段：

- 客户名称。
- 方案标题。
- 快速方案或 Deep Research。
- 方案创建时间和版本。
- TrustDecision。
- 情报快照状态。
- 是否有关联响应矩阵。

### 6.2 演练配置

| 配置 | 说明 |
|---|---|
| 客户角色 | 决策者、业务负责人、技术负责人、采购、法务/合规等 |
| 关注重点 | 价值、成本、周期、技术、案例、风险、合规、服务等 |
| 难度 | 基础、标准、挑战 |
| 模式 | 客户拜访、方案汇报、招标答辩、内部预演 |
| 轮数 | P0 建议 3—10 轮 |
| 是否即时反馈 | 每轮反馈或结束后统一反馈 |

系统可以根据客户画像和情报推荐配置，但员工必须确认后开始。

### 6.3 客户角色生成规则

- 角色只能基于已知客户岗位、业务目标和公开情报生成。
- 不得凭空补充客户私人经历、性格、政治倾向或敏感属性。
- 未知信息必须显示为模拟假设。
- 角色提示中必须明确“这是演练角色，不是真实客户观点”。

## 7. 多轮演练

### 7.1 客户提问生成

问题来源优先级：

1. 响应矩阵中的缺口和高风险要求。
2. Deep Research 的知识缺口与待确认问题。
3. 方案中的前置条件、风险和边界。
4. 客户画像中的目标、约束和关注点。
5. 公开情报中的近期动态和政策背景。
6. 通用销售异议模板。

### 7.2 问题类型

- 价值质疑。
- 竞品比较。
- 案例真实性。
- 企业能力边界。
- 实施周期和资源。
- 价格与投入产出。
- 安全、隐私和合规。
- 系统集成和运维。
- 失败风险和责任边界。
- 招标要求逐项追问。

### 7.3 多轮连续性

- 后续问题应读取本次演练已经发生的对话。
- 不重复已经充分回答的问题，除非客户角色明确表示不接受。
- 员工回避问题时允许追问。
- 员工提供新的事实时只能作为本次回答，不能自动成为已验证事实。
- 对话压缩不得丢失当前问题、客户角色、风险项和证据缺口。

## 8. 每轮回答评价

### 8.1 评价维度

| 维度 | 说明 |
|---|---|
| 事实与证据 | 回答是否有内部经验、能力或已确认客户信息支持 |
| 客户匹配度 | 是否回应当前角色和客户目标 |
| 完整性 | 是否回答问题主体、限制和下一步 |
| 风险控制 | 是否出现无依据数字、负责人、周期或保证 |
| 边界表达 | 是否区分事实、能力、推断和待确认信息 |
| 表达清晰度 | 是否简洁、易懂、结构清楚 |
| 推进效果 | 是否提出合理的确认问题或下一步 |

### 8.2 评价结果结构

每轮至少返回：

- 做得较好的部分。
- 需要改进的部分。
- 缺少的企业证据。
- 过度承诺或高风险表述。
- 建议回答框架。
- 建议追问。
- 引用的方案、画像或情报项。

不输出未经校准的“可信度百分比”。评分如需展示，只能作为本次演练内部等级，并说明不是绩效评分。

### 8.3 Trust Gate边界

- AI评价可以给出风险建议，但不能改变上游方案的 TrustDecision。
- 演练中发现的无依据事实进入报告的“待确认”，不能直接发布。
- 引用已撤销或过期来源时，评价必须标记无效。
- 外部公开信息不能作为企业能力或企业历史事实的证明。

## 9. 演练报告

### 9.1 报告内容

1. 演练基本信息。
2. 客户角色、模式、难度和轮数。
3. 覆盖的关键异议。
4. 回答表现总结。
5. 企业证据使用情况。
6. 无依据或过度承诺清单。
7. 未覆盖问题和知识缺口。
8. 建议补充的资料或专家问题。
9. 建议修改的方案段落。
10. 下一次演练建议。

### 9.2 报告操作

- 查看历史报告。
- 重新演练。
- 复制改进建议。
- 跳转回原方案。
- P1：创建方案修改提议。

报告不能一键自动覆盖正式方案；修改必须回到快速方案或 Deep Research 对应页面确认。

## 10. 与专家协作的关系

- 演练发现知识缺口时，可以生成建议专家问题。
- 只有演练上游是 Deep Research，且存在 `research_task_id` 时，才能跳转到该研究任务的专家协作。
- 不允许从演练直接创建一个没有 Deep Research 上下文的专家群。
- 专家回复回到原 Deep Research，再由员工决定是否重新生成方案和重新演练。

## 11. AI实现约束

- 演练使用单一编排流程或角色化 Prompt，不定义为 Multi-Agent。
- 不增加第六个 `AIEngine` 方法。
- 可通过共享模型适配层和V2业务服务实现角色生成、问题生成、回答评价和报告生成。
- Mock 与 Live 使用同一响应 Schema，并明确显示运行模式。
- Prompt、内部思维过程和完整未脱敏上下文不展示给业务用户。
- 模型失败不能使用固定优秀评价伪装成功。

## 12. 页面定义

### 12.1 演练列表

字段：

- 客户。
- 方案。
- 演练模式。
- 角色。
- 状态。
- 创建人。
- 创建时间。
- 已完成轮数。
- 上游可信状态。

筛选：客户、模式、状态、时间和创建人。

### 12.2 新建演练页

```text
第一步：选择客户和方案
第二步：确认画像、情报、响应矩阵和知识缺口
第三步：设置角色、关注点、难度和轮数
第四步：确认并开始
```

### 12.3 演练聊天室

```text
顶部：客户、方案、角色、难度、轮次和上游TrustDecision
左侧：对话记录
中间：员工回答输入区
右侧：本轮证据、风险、待确认和即时反馈
```

### 12.4 演练报告页

```text
顶部：演练总结
主体：异议覆盖、回答评价、证据使用、风险、知识缺口
底部：回到方案、重新演练、复制建议
```

## 13. 状态流转

```text
draft
→ ready
→ running
→ completed
→ archived
```

异常分支：

```text
ready/running → failed → retry
```

规则：

- `draft`：上下文或配置尚未确认。
- `ready`：快照已固化，可以开始。
- `running`：正在多轮演练。
- `completed`：报告已经生成。
- `failed`：模型或服务失败，保留已完成轮次。
- `archived`：员工主动归档，不删除审计记录。

这些是演练模块新增状态，不修改现有方案和研究状态。

## 15. 异常与恢复

- 上游方案不存在或无权限：禁止创建演练。
- 上游方案被 Trust Gate 阻断：可查看原因，不允许包装为正式方案演练；如保留内部练习，必须显示醒目标记。
- 情报来源失效：不显示可还原原文，并在上下文中标记失效。
- 模型生成问题失败：保留当前会话，允许重试，不重复计入轮数。
- 评价失败：员工回答保留，允许单独重试评价。
- 报告生成失败：保留全部轮次，可重新生成报告。
- 进程重启：从持久化的会话状态和最后完成轮次恢复。

## 16. 安全与伦理

- 页面持续说明“模拟客户，不代表真实客户观点”。
- 不根据敏感个人属性生成客户角色。
- 不诱导员工欺骗客户或隐瞒企业能力限制。
- 不使用演练结果进行未经确认的员工绩效评价。
- 客户画像、方案、证据和情报严格按 Workspace 与原始权限访问。
- 日志和后台摘要执行脱敏。
- 不保存模型内部思维过程。

## 18. 完成定义

“方案演练”完成必须同时满足：

1. 员工能够从两种入口使用相同的演练上下文。
2. 演练基于固定的客户、方案、情报和证据快照。
3. 客户问题与角色、业务目标、方案风险和历史对话相关。
4. 每轮回答都有结构化证据、风险、遗漏和改进反馈。
5. 无依据承诺和证据类型错误能够被识别。
6. 演练报告可追溯到轮次和上游版本。
7. 演练内容不自动修改画像、方案或知识资产。
8. 单模型流程不伪装成 Multi-Agent。
9. 任务可在 AI 后台观察，但业务操作只在演练页面完成。
10. V1/V1.1 回归测试全部通过。
